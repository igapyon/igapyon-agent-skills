# daybook：Waypoints の仕様検討

作成日：2026-10-20。状態：**名称・基本方針を採用し、Waypointsの操作手順をsource skillへ実装済み**。

## 1. 採用する名称と役割

> Waypoints は、task・activities を参照して、作業の再開地点を示す短いメモです。関連するスレッドへの参照も記録できます。

`waypoint` は経路上の中継点・通過点を表す。日をまたいで自分が戻る場合と、別セッションへ作業を引き継ぐ場合の両方で使う。利用者は、この名称とニュアンスを採用した。

Daybook リポジトリのルートに `waypoints/` を置き、複数の短い Markdown を保存する。各メモは作業への入口であり、スレッドの作成・実行・停止やリアルタイムの状態管理はハーネス側の機能として扱う。

## 2. 記録の役割と再開時の優先順位

| 記録・情報 | 役割 |
| --- | --- |
| task | 仕事の目的、現在の結論・状態、未解決事項、次の行動の正本 |
| activities | 実施内容、試行錯誤、判断理由、その時点の到達点の記録 |
| waypoint | 対象の作業、読むべき記録・資料、再開地点への短い案内 |
| 関連スレッド情報 | 確認できたスレッドとの対応、担当範囲、確認時点の状態 |
| Git状態 | 編集対象や未コミット変更の保全など、具体的な操作に必要な実態の確認 |

基本的な作業内容は task・activities に残し、会話履歴がなくても再開できるようにする。waypoint にだけ重要な進捗・決定・次の行動を置かない。詳しい説明を複製するより、短い再開文と参照で構成する。

再開は **対象task → 関連activities・資料 → 次の作業の把握 → 実行に必要な環境確認** を基本とする。taskを必要としない調査等は、そのactivitiesを入口にできる。Gitのブランチ名やclean/dirtyから、作業の目的・進捗・完了を推測しない。

古いwaypointと記録が食い違う場合は、task・activitiesと現在の利用者の依頼を確認して現在地を組み立てる。記録同士の食い違いは、出典や時点を確かめ、根拠のない完了扱いをしない。ファイル変更等を実行する段階では、対象リポジトリの実状態を確認して既存変更を保全する。

この分担は、現行の [task・activityの責務](../../skills/igapyon-miku-daybook/references/operations.md#task-and-activity-responsibilities) と [更新範囲・完了根拠](../../skills/igapyon-miku-daybook/references/operations.md#task-completion-and-scope) を土台にする。waypointの作成・更新だけでtaskのstatusやplanning stateを変更しない。

## 3. 配置とファイル名

```text
waypoints/
├── 20261020-1530-daybook-attachments.md
├── 20261020-1615-daybook-resume-design.md
└── 20261021-0900-recording-workflow.md
```

- 名前は `YYYYMMDD-HHMM-<topic>.md` とし、日時は作成時の Asia/Tokyo（JST）を使う。
- `<topic>` は内容が分かる短い英語の名前とする。
- 別の新規メモを作る際に同名が存在する場合は `.md` の前へ `-2` 等を付け、上書きを避ける。
- 同じメモを更新するときは、ファイルのパス・作成時刻のプレフィックス・番号を保持し、そのファイルを更新する。同名回避のための別ファイルは作らない。
- 同じtaskに関係するwaypointが複数あってもよい。再開範囲や関連セッションが異なる入口を残せる。
- 日時は一覧と識別に使う。最も新しいファイルが利用者の再開対象だとは限らない。

## 4. メモの内容

数行程度の自然な文章を基本とし、次を必要な範囲で含める。固定の長いテンプレートや追加のtask属性は必須にしない。

1. 何の作業を再開するか。
2. 読むべきtask・activities・資料への参照。
3. 再開時に最初に確認すること。
4. 分かっている場合、関連する別スレッドとその担当範囲・最終確認時点。

例：

```markdown
添付保存方針の作業を再開してください。
対象task: <taskへの相対リンク>
経緯: <関連activitiesへの相対リンク>
taskの最新状態と次の行動を確認してください。

別スレッドで作業中:
- スレッド: <分かっている名前、URLまたはID>
- 担当範囲: PDF変換仕様の検討
- 最終確認: 2026-10-20 15:30 JST
```

例の日時とスレッドは説明用である。実際のメモでは確認した情報だけを使う。Git情報は具体的な再開に必要な場合に添え、全メモの必須項目にはしない。

## 5. 関連スレッド情報

「実行中」は最終確認時点の情報として記録する。名前・URL・ID・担当範囲のうち判明しているものを使い、不明なIDや実行状態を推測しない。スレッドがあることだけでは、その作業が今も実行中だと判断しない。

再開側は、記録された別スレッドの担当範囲を確認し、同じ変更を二重に進めないようにする。古いメモから現在の実行状況を断定せず、必要な範囲で現在の情報を確認する。参照情報は実行中スレッドのロックや自動監視機構としては扱わない。

## 6. 作成・選択・再開の方針

- 作成時は、必要な基本情報がtask・activitiesにあるか確かめ、依頼範囲で必要な記録を整えてから再開文を書く。
- 再開ファイルが指定されている場合は、そのファイルを入口にする。
- 指定がない場合は依頼された作業内容から候補を絞る。複数の候補が区別できないときは、その点を確認する。更新日時だけで自動選択しない。
- メモを読む・候補を一覧する依頼と、実際の作業を再開する依頼の範囲を区別する。
- waypointに書かれた予定と、実行済み・承認待ち等の状態を区別する。実際の操作は現在の依頼範囲と該当する操作手順に従う。
- 別環境から使う場合は、参照した記録・成果物がその環境で読めるかを確認する。waypointの保存だけでGit反映や外部共有が済んだとは示さない。

## 7. 保存量とsource実装

waypointsには短い再開文と参照を置く。会話全文、task・activitiesの全文、原本ファイル、実行ログの複製を保存する場所にはしない。同じメモの更新と、新しい再開地点の作成を区別する。既存メモの一括削除やアーカイブの規則は、この合意だけでは追加しない。

source実装では、[SKILL.md](../../skills/igapyon-miku-daybook/SKILL.md) の操作分類と参照入口、[records.md](../../skills/igapyon-miku-daybook/references/records.md) のルート配置を更新し、新規 [waypoints.md](../../skills/igapyon-miku-daybook/references/waypoints.md) に保存・選択・再開手順を集約した。[operations.md](../../skills/igapyon-miku-daybook/references/operations.md) からも参照する。root [README.md](../../README.md) に利用例を追加した。

実daybookへの`waypoints/`作成や既存HANDOFFの移行は行っていない。必要なdaybookでWaypointsを使い始める依頼があった際に扱う。

## 8. front matter：更新日時と状態

利用者の提案に基づき、最終更新日時と状態をfront matterに持たせる。以下のフィールドと状態値をsource skillの規則として実装した。

```yaml
---
type: waypoint
updated_at: "2026-10-20T15:30:00+09:00"
status: ready
---
```

`updated_at`はメモの本文またはmetadataを実際に更新した日時とする。日時は時差付きで記録し、JSTを基本とする。読むだけ・同じ内容の再保存では更新しない。ファイル名の日時は作成時刻として維持し、最終更新日時とは別に扱う。

`status`は、そのwaypointの利用状態として次の3値を使う。

| 値 | 意味 |
| --- | --- |
| `ready` | 保存済みで、再開の入口として使える |
| `in_use` | このwaypointから再開したセッションが、自分の利用中状態として記録する |
| `closed` | 作業の区切り、後続メモへの置き換え等で、このwaypointからの再開が不要になった |

新規保存は`ready`、このメモから再開した際は`in_use`、再び中断して同じメモを再開用に整えた際は`ready`、この入口の役割が終われば`closed`とする。`closed`は削除ではなくファイルを保持する。別の`archived`状態は、保管と役割終了をさらに区別する必要が生じたときに検討する。

自分の利用状態は、再開・中断・役割終了を扱うセッション自身が、その操作の一部として更新する。別の監視役が稼働を確認して反映する方式にはしない。自分のスレッドの名前・URL・IDが分かる場合は、必要な参照も併せて更新できる。

waypointの`closed`はtaskの`done`を意味しない。別セッションや後続メモに引き継いだtaskは、引き続き進行中でもよい。taskの完了はtaskの記録と既存の完了根拠で判断する。

関連する別スレッドが実行中であることと、このwaypoint自体が利用中であることも区別する。別スレッドの状態・担当範囲・最終確認時点は、第5節のとおり本文へ必要な分だけ記録する。関連スレッドに動きがあるだけで、このメモを自動的に`in_use`へ変更しない。

`in_use`はリアルタイムの稼働保証や排他ロックには使わない。ハーネス停止や会話の中断を自動で反映できるとは限らないため、古い利用中表記は実際の状況を確かめて扱う。経過時間だけで`ready`や`closed`へ変更しない。

front matterなしの既存メモは、状態・更新日時が未記録として読む。ファイル名から最終更新日時を作ったり、無条件に`ready`と推定したりしない。新規メモは`type`、`updated_at`、`status`を持つ。

## 9. 操作方式：Daybookスキルに手順を置く

利用者は、再開したセッションが自分で更新する素直な方式を希望している。Daybookスキルに操作手順を持たせ、`waypoints/README.md`は必須にしない。source skillの入口と詳細referenceにこの手順を実装した。

| タイミング | 操作するセッションの動作 |
| --- | --- |
| 新しい再開メモを保存 | 必要な作業情報をtask・activitiesへ残し、waypointを`ready`で保存する |
| 指定されたwaypointから作業を再開 | 対象と依頼範囲を確認し、実作業に入る際に自分で`in_use`と`updated_at`を記録する |
| 明示的に中断・引き継ぎ | task・activitiesを依頼範囲で更新し、再開文を整えて`ready`へ戻す |
| この再開メモの役割が終了 | 自分で`closed`と`updated_at`を記録する。taskの完了は別に判断する |
| メモの閲覧・候補一覧だけ | 利用状態や更新日時を変更しない |

同じセッションで作業を続けるたびに利用中状態を書き直す必要はない。通常の操作・内容変更があった時点で更新し、heartbeat、定期ポーリング、期限による自動解除、排他ロックを初版の構成に加えない。

突然のセッション終了では`in_use`が残り得る。次の再開時にtask・activitiesと記録された担当範囲を読み、必要な現在状況を確認して扱う。この制約を隠すための稼働検知は追加しない。別スレッドの情報は、自分の利用状態と分けて、分かっている参照と担当範囲を必要な分だけ記録する。

## 10. サブ作業ごとに番号付きの入口を作る

利用者の依頼に基づき、計画時に1つの作業を複数のサブ作業へ分ける場合の番号付きwaypointをsource skillへ実装した。

### 役割と作成の粒度

サブ作業を個別に再開したり、別セッションへ渡したりするために、番号付きwaypointを使う。計画の分割内容・依存関係・完了条件・進捗はtask、またはtaskから参照する計画書に置く。waypointには、対象サブ作業の範囲、正本の該当箇所、再開時の最初の確認事項を短く記録する。

細かいチェック項目すべてにwaypointを生成する必要はない。独立した再開入口が必要な範囲で作成する。分割だけを理由にtaskも同数作ることはせず、日程や状態を個別管理する必要がある場合に別task化を検討する。

### ファイル名

```text
waypoints/
├── 20261020-1530-daybook-attachments.md
├── 20261020-1530-daybook-attachments-00001.md
├── 20261020-1530-daybook-attachments-00002.md
└── 20261020-1530-daybook-attachments-00003.md
```

番号なしは全体を再開する入口、番号付きは各サブ作業を再開する入口とする。例えば`00001`が保存方針、`00002`がOffice変換、`00003`がPDF変換を担当できる。全体の入口は、task・計画書と各サブ作業への案内だけに留める。taskや計画書だけで全体へ戻れる場合、番号なしのwaypointは省略できる。

- 共通部分`YYYYMMDD-HHMM-<topic>`で一連の作業をまとめ、末尾を`-00001`からの5桁連番にする。
- 番号付きファイルの日時は「共通の入口を最初に作った日時」を表す。後日に追加したサブ作業も共通部分を維持し、実際の更新日時は各ファイルの`updated_at`に記録する。この用途では第3節のファイルごとの作成日時規則を変更する。
- 番号は同じ共通部分の中での識別に使う。実行順、優先順位、改訂番号、task IDとして扱わない。
- 新しいサブ作業には、既存ファイルを確認して最大番号の次を割り当てる。`closed`の番号も再利用せず、計画の並べ替えでは既存ファイルを改名・採番し直さない。
- 同じサブ作業の再開文は既存ファイルを更新する。番号付きでない通常メモの同名回避`-2`とは用途を分け、番号付きメモの衝突時は次の未使用番号を選び、上書きしない。
- 全体の入口がある場合は、そこに担当範囲付きの子メモへの相対リンクを並べ、各子メモから全体へ戻る相対リンクを付ける。子の追加時は全体の案内を更新し、全体の入口を後から作る場合は既存の子にも戻り先を付ける。リンク更新だけでは各メモの状態を変えず、内容が変わったメモの`updated_at`だけ更新する。全体の入口を省略した場合は、子からtask・計画書へ直接リンクし、存在しない全体メモへのリンクを作らない。
- 各メモからtask・計画書の該当箇所へリンクする。親子用の新しいfront matterや、番号管理用の台帳は初版では必要としない。

短い子メモの例：

```markdown
---
type: waypoint
updated_at: "2026-10-20T15:30:00+09:00"
status: ready
---

PDFのテキスト化方針の検討を再開してください。
対象: <taskまたは計画書のPDFサブ作業へのリンク>
全体: <番号なしwaypointへの相対リンク。省略時はこの行も不要>
最初に、正本にある変換方法の候補と未解決事項を確認してください。
```

### 状態と別セッションでの利用

状態は各waypointを利用するセッションが個別に更新する。子を再開しただけで親や他の子を`in_use`にせず、親の状態を子へ一括反映しない。

子がすべて`closed`でも、taskや全体の入口を自動で完了扱いにしない。置き換え・引き継ぎによって子の役割が終わる場合もあるため、実際の完了は正本のサブ作業と完了根拠で判断する。

ファイルを分けたことだけでは、サブ作業を並行実行できるとは判断しない。再開時に計画の依存関係と、分かっている関連スレッドの担当範囲を確認する。番号付きメモの作成は、別スレッドの起動や作業開始を意味しない。

source実装は、後日追加でも共通部分を保持し、並べ替えで番号を変えず、置き換えによる`closed`でtaskを完了扱いにせず、task・計画書の詳細を各メモへ複製しない規則を含む。
