# Activity 記録モードの実装計画

## 1. Sol が実装する範囲

対象はこのリポジトリの [igapyon-miku-daybook](../../skills/igapyon-miku-daybook/SKILL.md)。会話の意味を解釈し、いつ、どの粒度で activity を保存するかは Agent の指示で実装する。実際の保存には既存の作成・更新 CLI を使う。今回の機能に、新しい CLI オプション、設定ファイル、front matter、バックグラウンド記録、既存データ移行は必要ない。

**Checkpoint Mode** を新たに daybook 利用を開始したときの既定とする。利用中のモードは現在の会話と利用者の指示から引き継ぐ。応答や話題が変わっても、それだけではリセットしない。利用者が「この調査の間だけ」と範囲を指定した場合はその範囲で適用し、終了後は元の頻度に戻す。

## 2. モードの意味と切替

| 状況・利用者の意図 | その場の扱い | 以後の頻度 |
| --- | --- | --- |
| daybook 利用を開始 | 作業内容を受け取り、切れ目で初回の記録を作る | Checkpoint Mode |
| 通常の調査・相談が続く | 同じ問いについての細かなやり取りは次の切れ目にまとめる | 現在のモード |
| 「activity記録して」「コマンドを記録して」「再現できるようにして」が activity 記録の指示として出た | その時点までの記録可能な未保存分を保存。全て保存済みなら書き込みはゼロ | Detailed Activity Mode |
| 「ここまでだけ記録して」など明確な単発指示 | 指定範囲の未保存分だけを保存 | 元のモード |
| 「activityあまり記録しないで」「再現性はあまり気にしないでいい」 | 切替そのものを記録にせず、次の切れ目で未保存分をまとめる | Checkpoint Mode |
| 「activityは記録しないで」「読み取りだけ」「このファイルだけ変更して」 | 指示が制限する範囲で activity 保存を抑止。記録禁止期間は再開後も自動で遡及しない | 利用者の範囲・再開指示に従う |

切替文言は意図を示す例として扱う。引用、仕様相談、資料内の文章は切替を指示しない。単独の「再現できるようにして」がソフトウェアの修正を求めている場面など、daybook の利用や記録頻度を意図していない場合には適用しない。一方、明確な daybook activity の記録依頼は初回の具体的な操作依頼にもなる。

## 3. 保存するタイミングと内容

**Checkpoint Mode** では「次に再開する人へ引き継ぐ内容が変わったか」で判断する。仮説を支持・否定する結果が得られた、方針が決まった、失敗によって次の試行が変わった、作業が完了・保留になった、別の話題に移る、といった節目が対象。応答の終端、ツール呼び出し、相づちだけでは書かない。一回の長い作業中でも切れ目はあり得る。保存時には直近の発言だけでなく、前回保存以降の目的、経緯、観察、判断、残件から再開に必要な内容を拾う。

**Detailed Activity Mode** では、目的のある一連のコマンド、試行、比較、判断が一まとまりになった時点で、そのエピソードにこまめに保存する。再現を求められたら、必要な作業場所・前提・入力、実際のコマンドと意味のある引数、観察した結果、そこから決めた次の手を記す。終了コードや出力は確認できた必要部分を使い、秘密値は伏せる。過去の未記録分を補うときも、確認できないコマンドや引数を推測して補わない。例えば条件を変えて二度実行したことは残し、同じ目的の準備コマンドは一緒に記録できる。

**両モード共通**。保存前に対象エピソードと既存本文を照合し、既にある事実を重複させない。同じ日の同じ作業は既存 activity を更新し、別のエピソードは必要に応じて別ファイルにする。新しい作業日、過去記録への日付付き訂正、日付をまたぐ連続作業には既存の編集規則を適用する。モード変更で新ファイルを割り当てない。保存失敗は未保存として報告し、記録済みと扱わない。

**既存操作との接点**。URL を受け取ったら、閲覧と必要な過去 activity の照合はその場で行う。元 URL と実際の閲覧結果は記録対象に含め、単独の URL 調査を終えたらその完了を切れ目とする。同じ調査に複数 URL がある場合は同じ activity にまとめられる。task・todo・topic 等の明示操作や、他の記録を作る前に出典 activity を保存する既存手順には、その操作上必要な時点で保存する。既にその場で保存した内容を応答末に二重保存しない。頻度変更から他レコードの作成や更新を推定しない。

## 4. 編集順序

1. [activity-capture.md](../../skills/igapyon-miku-daybook/references/activity-capture.md) を頻度判断の正本にする。既存の「Capture checkpoints and episode boundaries」の見出し・リンクを生かし、全モード共通になっている「最初の有用な事実」「実質的に進んだ応答ごとに保存」を上の判断に置き換える。切替表、単発指定、抑止指示の優先、URLや操作結果への適用をここで定義する。
2. [SKILL.md](../../skills/igapyon-miku-daybook/SKILL.md) の起動条件、話題変更、activity capture、保存ルーティングを確認する。入口には既定、切替例、正本へのリンクを簡潔に置く。「記録対象になる」と「このターンで書き込む」を区別する。
3. [operations.md](../../skills/igapyon-miku-daybook/references/operations.md) の「Task and activity responsibilities」「Add an activity」を整合させる。task 自体の更新タイミングは別の規則として読む。URL、todos、topics、Waypoints、Issue intake の参照先も、旧頻度を無条件に要求する箇所だけを見直す。新規作成時の衝突回避、更新ごとの本文・ハッシュの再読、古い記録の編集規則を引き続き使う。
4. [README.md](../../README.md) の利用者向け daybook 説明に、通常の動作と自然言語での切替例を示す。[DEVELOPMENT.md](../../DEVELOPMENT.md) の旧来の「実質的に進んだ応答の区切りで保存」を更新する。過去の設計計画は当時の経緯として扱う。

## 5. 受け入れ確認

Sol は使い捨ての daybook で会話例を確認し、各段階の**書き込み有無・対象ファイル・保存内容・次の応答での頻度**を見る。文言がドキュメントに存在するだけでは、頻度変更の確認にならない。

| 会話例 | 期待する結果 |
| --- | --- |
| 通常モードで一つの仮説について応答を数回往復し、その後に比較結果が出る | 途中の応答ごとには書かず、結果が出た時点で、問い・経緯・結果を一緒に保存 |
| 調査中に「コマンドを記録して」。その後に二つの異なる試行が完了 | 切替時に未保存分を保存。以後は各試行のコマンド・条件・結果を同じ activity に順次保存 |
| 通常モードで保存直後に「activity記録して」 | 新しい事実がなければ書き込みゼロ。次の試行では Detailed Activity Mode が働く |
| 通常モードで「ここまでだけ記録して」。次の応答は途中経過のみ | 指定分だけ保存。次の途中経過は切れ目まで保留 |
| 詳細モードで「あまり記録しないで」。続いて同じ目的の調査を数回行い、未解決のまま中断 | 通常モードに戻り、中断時に分かったこと・残る問い・次の確認を一緒に保存 |
| 「この間は記録しないで」→作業→「また記録して」 | 禁止期間を遡及して保存しない。再開以降の内容が対象 |
| URL閲覧が失敗／task更新時にactivityを先に保存／話題変更直前の内容が既に保存済み | 閲覧失敗は観察として残る。操作に必要な保存順を守る。保存済みの節目は重複しない |
| daybook 未起動で「『activity記録して』の仕様を検討したい」 | 設計上の発言を実操作にせず、daybook の探索・書き込みは発生しない |

最後に現行仕様のファイル内で旧頻度と新頻度の矛盾、相対リンク、変更差分を確認する。既存の `npm run test:daybook` は保存・更新ランタイムの回帰確認に使い、上記の会話判断とは別に結果を報告する。

## 6. 実装・確認結果

頻度と切替を activity-capture.md に定義し、SKILL.md、operations.md、README.md、DEVELOPMENT.md を合わせた。

- 会話例を手順に照らして読み合わせ、使い捨ての daybook で選んだ保存操作を実行した。同じ activity への継続、保存不要な場面でのハッシュの一致、停止中の内容が含まれないことを確認した。別セッションでの自然言語指示の自動評価は行っていない。
- `npm run test:daybook` は 99 件成功した。スキル形式の検証と `git diff --check` も通過した。
