# Sol 向け実装計画 — daybook レビュー指摘4件の修正

レビュー時の HEAD は `a17f0d0`。対象は [igapyon-miku-daybook](../../skills/igapyon-miku-daybook/SKILL.md) の同梱 CLI と対応するテスト・運用手順。以下のファイル名は特記がなければ同スキルの `assets/daybook/scripts/` 配下を指す。各項目は一時ディレクトリまたは模擬 API で不具合の条件を作り、修正前後の挙動を確かめる。

## 1. Issue 取り込み前にタスク ID の重複を検出する（P1）

同じ月の別 Issue から二つの計画を先に prepare すると、タイトル由来の保存先が異なっていても同じ月次 ID が選ばれる。先行する計画を apply した後、後続の計画も現在のパス検査を通過してしまう。

- `issue-import.mjs` の `verifyCurrentIssueSources` で、リポジトリロック取得後、最初の記録書き込み前に検出する。`scanIssueSources` が列挙済みの現行・旧配置のタスクを利用し、取り込み元 Issue の有無を問わず、完全な task-id と保存パスを照合する。移行済みタスクでは保存ディレクトリの月と ID の月が異なる場合もある。
- 計画と現存レコードで同じ ID が別パスを指す場合、既存の競合エラーに ID と両パスを含めて止める。採番済みの計画には手を加えず、利用者が再 prepare して新しい差分を確認できるようにする。同一パスは従来のハッシュ・出典検査に渡し、既存タスクへのリンクと部分適用の再開を維持する。
- **受け入れ条件**：異なる Issue・異なる保存パス・同じ ID の二計画を用意する。一つ目の apply は成功し、二つ目はその計画の記録を一件も書く前に停止する。再 prepare 後は別 ID で成功し、両タスクを含む daybook で日次計画を生成できる。`issue-import.test.mjs` の部分適用・再開ケースも通す。

## 2. Issue 取り込みの再開時にも受付コメントの下書きをそろえる（P2）

`applyIssueImport` は初回に `result.json` を保存した直後、Issue ごとの下書きを作成する。ここで処理が中断すると、再実行時に下書き作成が丸ごと飛ばされる。

- 初回の結果作成と既存結果の検証が合流した位置で、対象 Issue ごとに `comment-<番号>.md` を照合する。検証済みの計画から得た本文と末尾改行を正とし、欠落なら既存の排他的作成処理で復元、一致なら再利用、相違なら `LOCAL_CONFLICT` と対象パスを返す。この照合を記録の書き込みより先に完了させる。
- **受け入れ条件**：複数 Issue のうち一件だけ下書きがある中断状態から再開し、不足分だけが復元される。再々実行時も一致済みファイルを書き直さない。既存下書きが異なる場合は、その内容と適用済み記録を保ち、未適用の記録には進まない。結果ファイルに保存済みの投稿・クローズ状態も引き継ぐ。

## 3. activity の更新中に失敗しても元の本文を保持する（P2）

`activity-files.mjs` の `updateActivity` はハッシュ照合後に元ファイルを直接開いて書く。ファイルを切り詰めた後で書き込みが失敗すると、旧版の本文まで失われる。

- 同じディレクトリに一意な一時ファイルを排他的に作り、全文の書き込み、同期、クローズを完了する。既存ファイルのアクセス権を引き継ぐ。置換直前に既存のパス検証と SHA-256 照合を行い、一致した場合に rename する。エラー時は自分の一時ファイルを片づけ、元のエラーを呼び出し元に返す。
- 通常の更新 CLI と、保存済みの旧 Issue 計画からの activity 更新が同じ関数を使う。同期 API と既存の戻り値・競合コードを維持する。rename は途中の本文が見える問題を解決するが、最終照合と置換の間の同時更新まで排他するものではない。
- **受け入れ条件**：`update-activity.test.mjs` の既存の失敗テストは元パスへの直接書き込みをモックしているため、失敗を発生させる位置を更新する。一時ファイルの部分書き込み後の失敗、rename の失敗、最終照合での競合を個別に作り、元の本文または競合相手の本文がバイト単位で残ることを確認する。成功時は本文、権限、返却ハッシュを確認する。

## 4. 日次通知の手動再投稿で、応答喪失後の二重投稿を防ぐ（P2）

`post-day-plan.mjs` の `postDayPlan` は、手動の `allowDuplicate` 指定時、最初の POST が失敗すると再取得したコメントを無視してもう一度 POST する。GitHub が初回を受理して応答だけが失われた場合、一回の手動操作で通知が二件増える。

- 最初の POST 前に取得済みのコメント ID を保持する。手動再投稿の応答が不明なときは一覧を再取得し、開始後に増えた ID・対象日の Bot 通知・送信本文の一致を照合する。今回の投稿を一件特定できれば、既存の回復結果とその URL を返す。
- 再取得の失敗、反映待ち、複数候補などで受理の有無を特定できない場合、手動再投稿では自動で二度目の POST を行わず、対象 Issue と日付を含むエラーで結果不明を伝える。これは手動再投稿での二重送信を防ぐための設計判断。定時通知の既存の日付単位の抑止、旧マーカーの認識、dry-run の挙動も確認する。
- **受け入れ条件**：`post-day-plan.test.mjs` の模擬 fetch で、同日・同じ本文の過去コメントがある状態から開始する。新規コメントを保存した直後に応答エラーを投げ、再取得時に新規 ID が見える場合はその URL を返し、見えない場合は結果不明になることを確認する。どちらも POST は一回。通常の手動再投稿が成功すると一件増え、定時通知では既存の同日通知があれば POST はゼロ。

## 自己レビュー後の追加修正計画

### 1. 定時通知でも投稿の成否が不明なときは再送を止める（P2）

- `post-day-plan.mjs` の通常経路（定時通知、または `allow_duplicate` を指定しない手動実行）に残る二度目の POST を取り除く。初回 POST の失敗後はコメントを再取得する。同日の Bot 通知が確認できれば、既存の `skipped-after-uncertain-post` とその URL を返す。見つからない場合や再取得に失敗した場合は、対象リポジトリ、Issue 番号、対象日が分かるエラーで終了する。手動の `allow_duplicate` 指定では、今回追加されたコメントを ID と本文で照合する。
- 同梱の `.github/workflows/day-plan-notify.yml` で、投稿コマンドの終了コードを `tee` の後もワークフローへ伝える。投稿ステップで Bash の `pipefail` を有効にし、CLI が結果不明で終わった場合を失敗として表示する。`references/notification.md` には、結果不明時に対象 Issue のコメントを確認してから再実行する手順を書く。
- **受け入れ条件**。模擬 API で通常経路の POST を受理した直後に応答を失わせる。再取得で同日の通知が見えれば URL を返し、まだ見えない場合や再取得が失敗した場合は対象 Issue と日付付きのエラーになる。各ケースで POST は一回。事前に同日の通知がある場合は POST ゼロ。手動再投稿と dry-run の既存テストも通し、投稿ステップが CLI の非ゼロ終了を失敗として伝えることを確認する。

### 2. activity 更新の案内を実装に合わせる（P2）

- `references/activity-capture.md` の保存手順から、旧方式を前提とする「既存の合意を維持する」という記述を取り除く。更新の詳しい手順は `references/operations.md#add-an-activity` に集約する。元の本文と SHA-256 を同時に読み、元のハッシュを使って更新し、競合時は最新の本文を読み直す手順を残す。
- **受け入れ条件**。二つの運用文書を読み合わせ、既存のアクセス権を引き継いだ一時ファイルでの置換、置換直前の照合、照合から置換までに残る競合の余地が一貫していることを確認する。

追加修正後に `npm run test:daybook` と `git diff --check` を実行し、二つの受け入れ結果をこの計画に記録する。

### 追加修正の結果

- 通常投稿で応答を失った場合も、同日の Bot 通知が再取得で確認できれば URL を返す。通知がまだ見えない場合とコメント再取得の失敗は、Issue と対象日を示して停止する。全ケースで POST が一回だけであることを模擬 API テストで確認した。手動の `allow_duplicate` 経路も引き続き一回だけ POST する。
- 投稿ワークフローの Bash ステップに `set -euo pipefail` を加えた。失敗するコマンドを `tee` へつなぐ短い Bash 確認が非ゼロ終了し、パイプ内の CLI 失敗が Actions ステップに伝わることを確認した。
- `activity-capture.md` と `operations.md` の更新案内を合わせた。完全な一時ファイルの保存、アクセス権の保持、置換直前のハッシュ照合、最後の照合後にも同時更新が競合しうる点が両方に記載されている。
