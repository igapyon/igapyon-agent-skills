# daybook：添付をテキスト中心にする仕様案

作成日：2026-10-20。状態：**仕様検討案。運用ルールへの反映は後続工程**。

## 1. 目的と利用者の指定

Daybook の Git 管理下の容量が増え続けないよう、記録と補助資料を必要なテキストに絞る。画像・音声・動画の原本は原則格納しない。XLSX・DOCX などの Office 原本も極力格納せず、内容の保存が必要なら `igapyon-miku-ms-office` による Markdown 化を検討する。PDF もテキストへの変換を基本にする。

この文書は、その指定を具体的な保存判断・変換・例外・導入手順へ落とした提案である。対象は daybook の task、schedule、activity に付随する資料であり、この agent-skills リポジトリの配布用 runtime や教材画像へ一律に適用する規則ではない。

## 2. 現行仕様と変更の必要性

現在の次の案内は、渡された補助資料を形式にかかわらず保存する読み方になる。

| 調査した箇所 | 現行の案内 | 仕様反映時の変更 |
| --- | --- | --- |
| [SKILL.md](../../skills/igapyon-miku-daybook/SKILL.md) の添付案内 | supplied files を `attachments/<record-key>/` へ保存 | 保存前の判定とテキスト優先方針を入口に置く |
| [records.md](../../skills/igapyon-miku-daybook/references/records.md) の配置・リンク規則 | 補助ファイルを主記録と同じ月へ保存 | 保存対象は採用したテキスト資料と明示的な例外とする |
| [operations.md](../../skills/igapyon-miku-daybook/references/operations.md) の Store an attachment | supplied local file を保存 | 第3節以降の判断順序に置き換える |
| [DEVELOPMENT.md](../../DEVELOPMENT.md) の記録モデル | 資料を attachments に置く | 原本参照・テキスト保存・例外の区別を説明する |

既存の月別配置、record key、相対リンク、共有資料は1コピーという規則を引き継ぐ。task の front matter や day-plan のデータ契約には、新しい属性を追加する必要がない。現行 generator は添付本文を読まず、day-plan へ添付を複製しない。

## 3. 保存の判断順序

1. **記録の目的を満たす情報を決める。** 予定登録なら日時・場所・参加条件、活動記録なら経過・結果・根拠などを取り出す。資料を受け取ったことだけを理由に全文の保存を始めない。
2. **原本の参照先と必要な情報で足りる場合は、記録本文へ残す。** この場合は補助ファイルを増やさない。
3. **資料の本文を残す必要がある場合は、テキスト化して保存する。** 明示されたページ・シート・資料全体など、依頼された範囲を守る。
4. **テキストでは必要な情報を残せない場合は、制約を説明し、原本参照または個別の原本格納例外を扱う。** 変換に失敗したことを、原本を格納する理由へ自動的に読み替えない。

全文保存の依頼を無断で要約へ置き換えたり、一部だけ保存して全文であるように示したりしない。量が多い場合は、保存範囲を絞る案を出し、必要な全文と要約を区別する。

## 4. ファイル種別ごとの既定動作

| 入力 | 既定の扱い | Daybook に残すもの |
| --- | --- | --- |
| Markdown・プレーンテキスト | 目的に必要な内容を採用 | 記録本文、または `.md` / `.txt` の補助資料 |
| CSV・JSON・ログなどのテキスト | 必要範囲と量を確認。全量コピーを既定にしない | 必要なテキスト、選択範囲と参照先 |
| 画像 | 原本格納を避ける | 参照先と必要な説明。文字抽出を依頼された場合は抽出テキスト |
| 音声・動画 | 原本格納を避ける | 参照先と必要なメモ。依頼された文字起こし等はテキストで保存 |
| XLSX・DOCX・PPTX | 原本格納を避け、本文保存が必要なら Office-to-Markdown 変換を検討 | 必要な変換結果 `.md` と原本情報 |
| PDF | 原本格納を避け、本文保存が必要なら文字抽出、必要に応じて OCR | `.md` または `.txt` と原本情報・対象ページ・抽出方法 |
| その他のバイナリ・圧縮ファイル | まず原本参照と必要情報で扱う | 参照先と説明。格納する場合は第9節の例外 |

「小さい画像だから自動的に許可」などの形式別の抜け道は作らない。SVG のようなテキスト形式の画像も画像として扱う。本文中の簡潔なテキスト図は Markdown の記録表現として扱える。

base64、`data:` URL、画像・音声等を含む生の MIME、バイナリを文字列化した JSON、原本を包んだ ZIP などによる保存も、対応する原本と同じ扱いにする。拡張子が `.md` や `.txt` であることだけでは保存対象と判断しない。

## 5. Office 文書の変換

- XLSX / DOCX / PPTX の Markdown 化は、[Office スキルの案内](../../README.md#igapyon-miku-ms-office)にある `igapyon-miku-ms-office` の対応 converter を第一候補として検討する。
- 実際の利用時に同スキルの起動条件と runtime 手順を確認する。Office 資料が渡されたことだけで別スキルを無条件に起動したり、Daybook の必須依存にしたりしない。セッション内でその変換が既に明示的に依頼されている場合は、その依頼範囲で進める。
- 現行の同スキルはテキスト抽出を中心とし、画像・図形・グラフ・レイアウト等の保持を保証しない。セルの表示値、数式、注釈等についても、選択した converter の実際の出力を確認して保存内容を説明する。
- `.xls` / `.doc` などは、拡張子の付け替えで対応形式に見せない。対応する変換方法が確認できる範囲で扱い、未対応なら原本参照と必要情報を残す。
- 通常は主出力の Markdown だけを採用する。追加の画像、summary JSON、manifest、debug dump などを保存用に増やさない。
- Markdown 化しても容量が増える場合がある。大量の表・反復行・空の領域等が出力されたときは、依頼範囲に対して必要な内容かを確認する。converter にない範囲指定機能を想定しない。

## 6. PDF の文字抽出と OCR

PDF は利用環境にあるローカルの文字抽出手段を使い、特定のエンジンを Daybook の必須依存にはしない。候補には `pdftotext`、`pdfplumber`、`pypdf` などがある。実行時に利用可能性と出力を確認して選ぶ。

1. まず、対象範囲に読めるテキストがあるかを確認する。
2. 読める文字があれば抽出し、ページの対応・読み順・表や改行の崩れを確認する。必要に応じてページ単位で整理する。
3. スキャン等で必要部分に文字がない場合は、利用可能なローカル OCR を検討する。文字PDFとスキャンが混在する資料は、必要なページだけ OCR の対象にできる。
4. OCR を使った部分を明記し、誤認識や不鮮明な箇所を確定した原文のように扱わない。日付・金額等、今回の記録に使う重要な値は原本と照合する。
5. 抽出できない、または必要な内容を保持できない場合は、その範囲と理由を残す。空の出力を変換成功とはしない。

図、レイアウト、署名などがテキストへ移らない場合、必要な参照箇所と制約を記す。表を崩れた順序のまま確定情報として取り込まない。全文保存の依頼なら、取り出せなかったページを明示する。

OCR や確認のために生成するページ画像、OCR 済み PDF、途中の HTML 等は作業用であり、Daybook の保存対象にはしない。ローカルの変換手段が不足していても、外部サービスへのアップロードを自動的に始めない。

## 7. 保存場所と原本情報

変換・抽出した補助文書は、既存の `YYYY/YYYYMM/attachments/<record-key>/` に置く。task なら完全な task ID、schedule/activity なら従来の filename stem を key とする。変換結果は UTF-8 の `.md` を基本とし、プレーンテキストが適切な場合は `.txt` も扱える。

記録本文は要点と補助文書への相対リンクを持つ。別の task や activity でも同じ資料を使う場合は、その1コピーを参照する。生成 day-plan に本文や補助ファイルを複製しない。

補助文書の冒頭には、今回必要な項目だけを短く置く。別の metadata ファイルは作らない。

```markdown
# 会合資料（テキスト抽出）

- 原本名: briefing.pdf
- 原本参照先: 提供された継続利用可能なURL等がある場合に記載
- 対象範囲: 2〜4ページ
- 方法: PDF文字抽出、3ページのみOCR
- 変換日: 2026-10-20
- 制約: 4ページの図は含みません。図の確認は原本を参照してください。

## 抽出本文

……
```

抽出、OCR、要約を区別する。原本全体のコピーではない場合は対象範囲を明示する。converter の版数や原本のハッシュは識別に必要なときだけ追加し、取得していない値を推測しない。

原本参照先は、提供済みのURLや利用者が指定した継続利用可能な保存先を使う。外部への移動・アップロード・共有設定変更は別の操作である。参照先がない場合は原本名と「原本保存先は未指定」を記載できる。存在しないURLを作ったり、一時ファイルや端末固有の絶対パスを恒久リンクとして保存したりしない。Daybook 外の原本保管が完了したとは示さない。

## 8. 作業ファイル、再変換、容量

### 作業ファイルの配置

原本コピーや変換中間物は、Git 管理の候補に入る場所へ置かない。対象 daybook に `workplace/` 等がある場合も、実際に Git の ignore 対象であると確認してから使う。確認できなければ、リポジトリ外の一時領域を使う。フォルダ名だけを根拠に ignore 済みと判断しない。

`git add --all` の対象になり得るため、原本や中間物をいったん `attachments/` にコピーして後で消す手順は採らない。変換後の必要なテキストだけを最終配置する。画像へのリンクが生成された場合は、失われる情報を説明し、一時ファイルへのリンクや画像のbase64埋め込みを残さない。

### 再変換と重複

同じ資料の同じ内容が既にあれば再利用する。更新依頼で既存の補助文書が特定できる場合は、変換内容の差分を確認して同じ文書を更新する。依頼がない同名ファイルの上書きはしない。別資料の同名衝突は既存資料と取り違えず、一意な名前を付けるか必要な識別だけ確認する。

変換するたびに日付付きの原本・Markdown・抽出ログを一式保存しない。同内容の再抽出ではファイルを書き直さず、変換日の変更だけの差分も作らない。別版の保存は、その必要性が依頼に含まれる場合に限る。

### 容量の確認

初版では、一律のバイト上限は設けない。資料の実態を調べず任意の上限を置くより、原本・中間物・不要な全文・重複の流入を防ぐことを先に適用する。

保存時は、今回追加・更新する補助文書の容量、内容、ファイル数を確認する。依頼範囲に対して大きな抽出結果なら、参照のみ・対象範囲の抽出・要約の選択肢を示す。分割や圧縮で総量を隠さず、必要な全文保存を無断で省略しない。容量上限や自動検査が必要になった場合は、実データの棚卸しを基に後続仕様として決める。

## 9. 原本を格納する個別例外

必要な情報をテキストと原本参照で扱えず、利用者がその原本を Daybook の Git 管理下へ入れる意図を明示した場合は、個別例外として扱える。原本の種類、容量、保持理由を確認し、記録本文へ短く残す。

通常の「資料を添付して」「これを記録して」だけでは、原則を上書きする原本格納の意図とみなさない。一方で、「このPDFは例外として原本をGit管理して」のように例外が明示されていれば、同じ内容の承認を重ねない。例外はその対象だけに適用し、他のファイルや将来の取り込みへ広げない。

例外原本は既存の配置・重複回避・上書き防止規則で扱う。使う記録から参照し、原本と同じ内容を別の月や day-plan に複製しない。

## 10. 既存データへの導入

新規の添付・既存資料の更新時から適用する。既存のリンク、添付、task ID を通常の記録編集で一括変更しない。

既存添付の整理を依頼された場合は、Git 追跡中の添付について形式・容量・参照元を棚卸しし、個別に「外部原本参照とテキストへ置換」「例外として維持」を検討する。外部の保存先と必要な内容を確認してからリンクを変更し、削除はその依頼範囲で行う。

現行ファイルから原本を削除しても、過去の Git 履歴には残る。この仕様の主目的は今後の増加を抑えることであり、既存履歴の容量削減は別の移行作業として扱う。

## 11. 振る舞いの確認例

| 入力・状況 | 期待する振る舞い |
| --- | --- |
| 案内PDFから予定を登録 | 必要な予定情報と原本参照を記録。原本と全文抽出を自動保存しない |
| PDFの本文全体を資料として保存 | 全体を文字抽出し、必要なOCRを含むテキストを保存。未抽出部分は明示 |
| スキャンPDF、ローカルOCRなし | 抽出不足と使える原本参照を記録。PDFやページ画像の格納へ自動的に切り替えない |
| miku-ms-officeでXLSXをMD化してtaskへ保存 | 対応converterの主出力を採用。原本と追加画像等を保存対象にしない |
| 変換結果に図表が欠ける | 対象箇所と制約を記録。完全な原本再現と説明しない |
| 変換Markdownに画像への一時リンクがある | リンクを恒久的な資料と誤認させず、参照原本と欠落内容を説明 |
| 小さなPNG、またはSVGが渡された | 画像原本格納の既定は変わらない |
| 録音・動画が資料として渡された | 原本参照と必要な記録で扱う。文字起こし依頼があればテキストを扱う |
| 拡張子.mdにbase64の画像が入っている | テキスト資料の許可を迂回する原本保存として扱う |
| 複数の記録が同じ抽出資料を使う | 主記録の月に1コピー保存し、他の記録からリンク |
| 同一内容の再変換 | 既存文書を再利用し、日時だけの差分や複製を作らない |
| 同名だが別の資料 | 既存文書を上書きしない |
| 原本格納の例外が明示されている | 対象・容量・理由を残して個別対応。同じ承認を重ねない |
| 既存添付に画像やPDFがある | 通常編集では保持。整理の依頼時に棚卸しして判断 |

## 12. 仕様を反映する際の構成

1. 詳細ルールを新規の `skills/igapyon-miku-daybook/references/attachments.md` へ集約する。形式判断・変換・例外が必要なときに読む入口を作る。
2. `SKILL.md` の添付案内と first checks から詳細へ接続する。
3. `records.md` の保存対象・パス・リンク規則と、`operations.md` の Store an attachment を整合する。長い活動の補助資料へ分ける案内も同じ方針へ接続する。
4. `DEVELOPMENT.md` の添付の説明を更新する。README は利用者に必要な短い説明を検討する。
5. 第11節のケース、リンク到達性、矛盾する旧保存案内の残存を確認する。実際の変換を試す場合は、対象形式に応じた代表資料で必要内容と中間物の配置を確認する。

初版の反映はエージェントの保存判断・操作規則を対象とする。generator の選択処理や Issue import の schema を変更したり、実 daybook へデータ移行を自動適用したりする必要はない。専用の監査CLIやGit hookは、この案の必須要件に含めない。

## 検討時点の記録

2026-10-20に現行 daybook source の添付案内、Office スキルの対応形式・テキスト中心の制約、PDF スキルの文字抽出案内を参照した。実資料の変換や対象 daybook の容量調査は行っていない。したがって容量削減率、変換の完全性、OCRの成功率はこの案では保証しない。
