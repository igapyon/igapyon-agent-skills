# daybook 実運用からのスキル改善メモ

記録日：2026-10-26。対象：`skills/igapyon-miku-daybook/`。

実運用で得た知見と改善候補を蓄積する。MIT資料を根拠の支えとし、利用者の実運用知見と合わせて記録方針を判断する、という位置づけと、項目2・3の判断基準は、2026-10-26 にスキルへ反映した。項目1の `npm ci` の見直しは改善候補として継続する。

## 1. day-plan 生成前の npm ci を必要な場合に絞る

### 観察

`references/operations.md` の「Generate a day-plan」は、`npm ci` に続けて生成コマンドを案内している。

2026-10-26 に実 daybook で、既存の依存関係を使い、次のコマンドだけで当日の day-plan を生成できた。

```sh
node scripts/generate-day-plan.mjs --date 2026-10-26
```

### 改善候補

依存関係が導入済みで使える通常運用では、生成コマンドを直接実行できるように案内する。依存関係の初回導入・更新や、クリーンな環境の再現が必要な場面で `npm ci` などの準備手順を案内する。

今回確認したのは既存環境で生成できたこと。依存関係と lockfile の整合性をどの程度確認するかは、反映時の検討事項とする。

## 2. 記録先に迷う場合は activities を入口にする

### 利用者の運用知見

使い始めた頃は、activities と task のどちらに入れるべきか迷い、判断が揺れることが多かった。これまで実際に使った経験から、迷いそうな場合や、特段 task として扱う理由が強くない場合には、どんどん activities に記録するのがよい。

分類に迷って記録が滞ることを減らし、実施内容・調査・試行錯誤・気づきを気軽に残せる入口にする。

### スキルに反映した判断

- 実際に行ったこと、調べたこと、考えたこと、観察や気づきは activities に記録する。結論や完了がなくても記録できる。
- 記録先が曖昧で、task として管理する意図が明確でなければ、activities を選ぶ。分類だけの確認で記録を止めない。
- これから行う作業の登録や、既存 task の最新状態・次の行動を管理する依頼は task として扱う。
- 活動の文章に具体的な作業が含まれることや、関連 task があることだけで、task の新規作成・更新を追加しない。既存の編集範囲と完了根拠のルールを引き続き適用する。

### 反映箇所

[SKILL.md](../../skills/igapyon-miku-daybook/SKILL.md) の依頼分類・activity の案内と、[operations.md](../../skills/igapyon-miku-daybook/references/operations.md) の task と activity の役割説明に、迷った場合の判断を加えた。task 登録の説明も、これから行う作業を登録する依頼に対する指示であることを明確にした。

既存の「task は最新状態と次の行動、activities はその日に実際に行ったことや判断の経緯」という分担を、記録し始めるときにも使いやすくする。

## 3. 日々の記録は activities に集め、必要なときに整理して task へ反映する

### 利用者の運用知見

activities と task の両方に同じ内容を書きたくなりがちだが、実際に運用して、重複記載を避けるべきだと気づいた。日々の事実や経緯を入れる先は activities とし、必要なら activities をまとめて整理し、task に反映する。

### スキルに反映した判断

- 実施内容・調査・試行錯誤・判断理由は activities に集約し、同じ出来事や経緯を task に重ねて書かない。
- task への反映が必要になったときに、関係する activities を読み、現在の結論・状態・未解決事項・次の行動を整理して反映する。複数日にわたる活動も整理の対象にできる。
- task から経緯をたどれるよう、根拠となる activities への相対リンクを付ける。詳細の再掲を避け、task は現在の作業を把握できる内容に保つ。
- activities は当時の記録として保持する。task への整理・反映によって、元の活動記録を移動・削除しない。
- activities を記録するたびに task を更新する運用にはしない。必要な task への反映を依頼された範囲で行い、既存の編集範囲と完了根拠のルールを適用する。

上記の記録の流れを、`SKILL.md` の activity の案内と `references/operations.md` の「Task and activity responsibilities」に明記した。

## 4. task 用の添付フォルダ名は task-id と呼ぶ

`record-key` という総称では task の識別子との関係が伝わりにくいため、task 用の添付パスを `attachments/<task-id>/` と説明する。`task-id` は既存の front matter の `id`（`task-YYYYMM-NNNNN`）を指す。

activity・schedule の添付先は、それぞれ拡張子を除いた記録ファイル名を使う形で別に説明する。2026-10-26 にスキルと関連文書の用語へ反映した。

同日、`SKILL.md` の用語節と `references/records.md` に、`task-id` を task の永続的な識別子として明示的に定義した。front matter の `id`、記録ファイル名のID部分、添付フォルダ名が同じ値を使うことを説明し、task 更新手順でもこの用語を使うようにした。
