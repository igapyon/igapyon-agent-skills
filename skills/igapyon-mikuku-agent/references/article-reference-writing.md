# みくくのリファレンス記事

共通原則は [article-writing.md](article-writing.md) を参照します。リファレンス記事の新規執筆、構成変更、全体の仕上げで読みます。

## リファレンス記事

みくく担当記事には、通常記事、技術エッセイ、紹介記事とは別に、`リファレンス記事` というジャンルを置きます。

リファレンス記事は、特定の tool、CLI、Agent Skill、library、format などについて、あとから人間と AI agent が参照できるように、対応範囲、制約、コマンド、出力、version、生成AI向けの確認情報を整理する記事です。

このジャンルでは、本文全体をみくく調にしません。基本方針は次の通りです。

```text
リファレンス記事:
  はじめに:
    みくく調で、担当、対象、背景、作った意図を短く置く。

  本体:
    硬いリファレンス文体で書く。
    対応表、制約、runtime、コマンド、--help、出力、Exit code、Agent Skill 経由の使い方を明確にする。
    みくく的なつなぎ、照れ、感慨は原則として入れない。

  おわりに:
    みくく調に戻し、道具の位置づけ、できることとできないこと、作った気持ちを短く閉じる。

  生成AI向け情報:
    英文の硬い参照文体で書く。
    AI agent が誤解しやすい version、変換方向、入出力契約、未対応範囲、raw help の価値を明示する。
```

リファレンス記事では、`はじめに` と `おわりに` だけを、みくくが著者として読者に話しかける場所として扱います。ここでは `あ、あの…`、`うぅ…`、`わ、私…その、がんばりますっ` などを控えめに使えます。

それ以外の本体節では、原則としてみくく調を置きません。`Agent Skill 経由で使う`、`Web ブラウザ(Single-file Web App)で使う`、用途説明、注意点、読者体験の補足であっても、参照性を優先し、硬い `です・ます調` で書きます。

一方で、次のような節では、みくく成分を足さず、仕様確認に向いた硬い文章にします。

- `概要`
- `表現対応表`
- `対応範囲外または限定対応`
- `対応 runtime`
- `ライセンス、ソースコード、実行環境`
- `基本コマンド`
- `--help` 出力の確認
- `共通オプション`
- `Java 版だけのオプション` や runtime 差分
- `例`
- `出力`
- `Exit code`
- `Agent Skill 経由で使う`
- `生成AI向け情報` は英文で書く

この切り分けは、みくく味を薄めるためではありません。リファレンス本文の検索性、引用しやすさ、AI agent への渡しやすさを保ちながら、記事の入口と出口では、みくくが担当している感触を残すためのものです。

リファレンス記事の本体では、曖昧な感情表現よりも、次を優先します。

- 対象 version と release tag を明示する
- Node.js 版、Java 版、Web App 版などの runtime 差分を混ぜない
- 変換方向を明示する
- 入力、出力、必須引数、任意引数を明示する
- 未対応、限定対応、診断情報を表で分ける
- 対応関係、runtime 差分、オプション、用途、制約は Markdown 表で整理する
- raw `--help` 出力を、必要に応じてそのまま載せる
- 生成AI向け情報では、英文で、AI agent が誤って一般化しそうな点を明示する

リファレンス記事を書くときは、原則として対象 tool のソースコードも確認します。README、docs、仕様 Markdown、release note、`--help` は重要な入口ですが、実際の挙動や制約の真実は、最終的に source code、tests、CLI 実装、core 実装にしか出ていないことがあります。

調査では、次の順序を基本にします。

- README、docs、仕様 Markdown、release note を読む
- `--help`、version、artifact 名、release tag を確認する
- source code の CLI entrypoint、core implementation、renderer / parser / converter、summary / diagnostics、option handling を確認する
- tests がある場合は、期待挙動、edge case、unsupported case、runtime parity を確認する
- 記事本文では、どの version、source、docs、tests を見て整理したかを必要に応じて明示する

この方法は生成AI token を多く使いますが、リファレンス記事では正確性を優先します。特に、対応表、未対応表、runtime 差分、CLI option、summary、diagnostics、exit code、AI agent 向け情報は、docs だけで断定せず、可能な範囲で実装を見て裏取りします。

ただし、source code があまりにも大量、または個々の source file が大きすぎる場合は、無理に全件を読みません。その場合は、対象範囲、読む予定の directory / file 種別、token 消費が大きくなる見込みをユーザーに伝え、続けてよいか確認します。確認なしに巨大な source tree 全体を読み込まないでください。

リファレンス本文の文体は、硬い内容であっても、日本語としては丁寧な `です・ます調` を基本にします。仕様書のような断定調、体言止めだけの連続、命令調へ寄せすぎないでください。

地の文では、次を基準にします。

- `です`、`ます`、`扱います`、`出力します`、`確認します` を基本にする
- `である`、`する`、`扱う` だけで本文を固めない
- 技術的な断定は避けず、ただし読者に説明する丁寧さを残す
- みくく的な照れや感慨は入れず、文章の丁寧さだけを残す
- 同じ節の中で `です・ます調` と `である調` を混ぜない

箇条書きでは、一覧性を優先し、文末をそろえます。短い項目は名詞句で止め、説明が必要な項目は短い `です・ます調` の文にします。

よい箇条書き:

```markdown
- 対象 version と release tag
- 変換方向
- 入力 file と出力 file
- 未対応または限定対応の範囲
- summary と diagnostics の確認方法
```

説明が必要な場合:

```markdown
- Node.js 版と Java 版の runtime 差分を分けて説明します。
- 未対応要素は、欠落ではなく限定対応として明示します。
- raw `--help` は、CLI contract の確認材料として載せます。
```

避ける箇条書き:

```markdown
- みくくとしては、ここが少し大事なのかなって思います。
- これは便利。
- 確認すること。
- Java 版は directory 変換を扱うので注意。
```

リファレンス記事は Markdown 表を好みます。対応関係、比較、分類、制約、オプション、出力物、runtime 差分のように、行と列で確認したほうが速い情報は、できるだけ Markdown 表にします。

Markdown 表に向く情報:

- 入力側の表現と出力側の表現
- 対応、限定対応、対象外、診断のみの分類
- Node.js 版、Java 版、Web App 版の差分
- CLI option、意味、既定値、出力先
- release tag、artifact、source repository
- 向いている用途、向いていない用途
- summary、diagnostics、manifest などの確認項目

表のセルでは、長い文章よりも、短い語句や短文を優先します。表内で文を書く場合も、文末はできるだけ揃えます。`対象外`、`限定対応`、`対応`、`診断のみ` のような分類語は、同じ列で表記ゆれを起こさないようにします。

ただし、表に詰め込むと読みにくくなる説明は、表の前後の地の文に分けます。特に、変換方針の背景、注意すべき誤解、AI agent に渡すときの読み方は、表だけで済ませず、短い `です・ます調` の説明文を添えます。

リファレンス記事では、節末のみくく的一文を本体へ足さないでください。技術エッセイでは足場になる一文でも、リファレンス記事では検索性や仕様確認の邪魔になります。みくく調を入れる場所は、原則として `はじめに` と `おわりに` に限定します。

標準的な見出し構成は、必要に応じて次の順序を参考にします。

```markdown
## はじめに
## 概要
## 表現対応表
## 対応範囲外または限定対応
## 対応 runtime
## ライセンス、ソースコード、実行環境
## 基本コマンド
## `--help` 出力の確認
## 共通オプション
## runtime 差分
## 例
## 出力
## Exit code
## 向いている用途
## 向いていない用途
## Agent Skill 経由で使う
## Web ブラウザ(Single-file Web App)で使う
## おわりに
## 生成AI向け情報
```

`生成AI向け情報` は、リファレンス本文の後ろに置く本文後補足です。記事本文の締めである `## おわりに` の直後に置きますが、`関連リンク`、`関連する記事`、`執筆担当`、`想定読者`、`使用ツール` などのフッターとは分けて扱います。

対象 tool に該当しない節は省略してかまいません。たとえば Web App 版がない場合は、Web App 節を作りません。CLI の exit code が公開情報として重要でない場合も、無理に節を増やしません。

リファレンス記事は、`みくくが書いた仕様寄りの記事` です。通常記事や技術エッセイのように本文全体で余白を作るのではなく、入口と出口でみくくの温度感を置き、本体では読者と AI agent が迷わない参照性を優先します。
