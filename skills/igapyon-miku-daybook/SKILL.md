# igapyon-miku-daybook

Manage the Markdown records in a daybook repository. The records are the source of truth; generated day-plans and GitHub notifications are derived views.

The bundled `.mjs` command-line tools run with Node.js and the files in this skill; they do not require `npm install` or `npm ci`.

The recording policy is informed by both the user's practical daybook experience and MIT OpenCourseWare's [Guidelines for Keeping a Laboratory Notebook](https://ocw.mit.edu/courses/7-16-experimental-molecular-biology-biotechnology-ii-spring-2005/b4c64ac11fc0a68466af7e025e29bf3e_lab_notebook.pdf), a course resource for *7.16 Experimental Molecular Biology: Biotechnology II* (Spring 2005). Use the material's guidance on prompt recording, observations and results, and review and next steps as supporting rationale for recording decisions. Activity capture, deferred todos, optional task/topic consolidation, and the day-based activity editing policy are daybook-specific judgments developed from that guidance and experience.

Activities can support starting, continuing, and resuming work without a task. Keep dated work, ideas, trials, observations, and decision reasons in activities. Tasks manage a particular job's purpose, completion conditions, progress, remaining work, and next actions, keeping the short conclusion needed to act. [Topics](references/topics.md) maintain thematic knowledge, specifications, adopted decisions, and current understanding, with source links. Create them as needed within scope; an activity can lead directly to a topic. Keep task details light by referring to topics rather than maintaining the same detailed account twice. See [record responsibilities](references/operations.md#task-and-activity-responsibilities) for the editing rules.

Keep separately deferred actions in [todos](references/todos.md), with links to the activities where they arose. Todos remain discoverable across days without required task planning; they can be completed through activities or handed over to a task.

When the user combines daybook with other documents or workflows, follow their chosen division of responsibilities and authoritative sources. Keep updates within the requested scope and avoid maintaining the same work state in multiple places by default.

Unless the user specifies another style, write narrative prose in daybook records in Japanese polite form (です・ます調). Bullet items may use concise plain-form sentences or noun phrases; do not force polite endings on every bullet.

## Terminology

`task-id` (task ID) is a task's persistent identifier: its front matter `id` value in `task-YYYYMM-NNNNN` format, for example `task-202610-00014`. The same value forms the task filename's ID prefix and its attachment folder name. Use `task-id` when referring to this identifier; keep the YAML field name as `id`.

A `todo-id` identifies a deferred action in `todo-YYYYMM-NNNNN` format. A todo record has `type: todo`; a task's `status: todo` still means an unstarted task.

A `topic` record is a maintained thematic summary under `topics/`. A conversational topic or topic change does not by itself request such a file.

## Activation and boundaries

Initially activate only for a clear request to use daybook or perform a daybook operation, or a current repository instruction that explicitly directs use of this skill. A name mention, quoted or historical handoff text, general TODO/productivity discussion, Issue or URL reading, and questions, review, or edits about this skill alone do not initially activate record operations. Once active, continue daybook use across follow-up messages and topic changes without requiring another invocation. An explicit URL-to-task lookup, GitHub Issue import, or notification operation still requires its specific request; ordinary URL receipt follows the activity procedure below.

This skill manages daybook records, local documentation, an explicitly requested notification workflow, and the resume context for daybook-managed work. It does not automatically commit, push, create pull requests, dispatch workflows, send email, or synchronize Issues with tasks. Explicit Issue intake is a narrow exception: follow [issue-import.md](references/issue-import.md) to prepare local records, then use the bundled miku-scm skill's comment and close workflows for the intake receipt and verified intake close. The daybook request authorizes that bounded workflow, but does not bypass miku-scm's current Issue snapshot, preflight, approval, apply, and attempt-recovery requirements. Do not post comments or close Issues for an Issue read, candidate list, ordinary daybook update, or resumed import unless the user's request covers that action.

Daybook-managed work can take place in another directory or repository. Use the daybook records to identify and resume the requested work, then follow the work location's instructions and applicable workflow. Keep repository references one-way: daybook may reference the work repository, its files, and its results; do not add links, paths, or resume pointers back to daybook in the work repository's files or repository-facing text. Keep daybook-specific recording and resume context on the daybook side. See [Find and resume earlier work](references/activity-capture.md#find-and-resume-earlier-work) for the handoff procedure.

Weekly recurrence is maintained only for an explicit weekly-task registration or rollover request, following [operations.md](references/operations.md). Ordinary record edits and migrations do not trigger recurrence-field initialization, an additional weekly-task scan, or rollover. For rollover, process only the requested tasks; process all active weekly tasks only when the user explicitly requests that scope. The skill does not run in the background. Lists and explanations keep the records being inspected unchanged and follow the common activity capture below. Day-plan generation may write or overwrite its generated snapshot, but must not modify source task or schedule records.

## Startup and request routing

The current user's instructions take precedence over earlier conversation and repository handoff instructions. Carry forward any still-applicable operation from those sources. If an operation is specified, proceed within that scope; otherwise briefly acknowledge readiness and wait, deferring target-daybook discovery, README/Git checks, record reads, and operation-specific references.

After activation, a user-provided URL or a substantive discussion is eligible for activity capture even without an explicit recording command. Use the current mode below to decide when to save. Reading this skill for a meta task does not itself establish active daybook use. An ordinary end-of-work or pause signal triggers the final checkpoint below. A request to stop recording or a restriction on file changes takes effect as stated and suppresses any disallowed save. Leave an excluded interval out of later saves unless the user explicitly requests its material.

For an activity list, history question, or request to resume daybook-managed work, follow [Find and resume earlier work](references/activity-capture.md#find-and-resume-earlier-work). Use the date and subject to find the entry, then follow its previous links as needed. A history question calls for lookup and explanation. If the user names a [legacy waypoint](references/waypoints.md), read it for resumption context.

Once an operation is known, read only the records and supporting material needed for it. Use scoped filename or content searches to locate unknown records rather than loading the repository's records in advance.

During active use, at the start of each substantive topic, consider whether existing daybook records help interpret the user's meaning before forming the answer. Use the conversation and relevant records as context, including implied references without a task-id; consult further records only as needed. A topic change does not itself erase that context. Follow [topic context](references/activity-capture.md#interpret-a-new-topic-in-context) for scoped reads and uncertain connections. Keep the current request authoritative, and do not turn a speculative connection into a confirmed task association, task edit, or activity merge.

## Activity capture during active use

Activity is the common record of meaningful conversation progress, user-provided URLs, and operation outcomes during active daybook use. In the default **Checkpoint Mode**, save the relevant unsaved material at a meaningful work boundary, such as a finding, decision, pause, or topic change. In **Detailed Activity Mode**, save at each meaningful group of attempts or commands. Before sending a final reply, handle any save due under the current mode. Follow [Save and report the record](references/activity-capture.md#save-and-report-the-record) when a save fails or its outcome is uncertain.

When used as activity instructions, “activity記録して”, “コマンドを記録して”, and “再現できるようにして” request a save of eligible unsaved material and switch to Detailed Activity Mode. A one-off save keeps the current mode. “activityあまり記録しないで” returns to Checkpoint Mode. Follow [activity-capture.md](references/activity-capture.md#choose-the-recording-mode) for switching, save timing, and restrictions.

Use the existing [activity CLIs](references/operations.md#add-an-activity) and continue the same episode in its existing activity under the [date editing rules](references/activity-capture.md#edit-activities-over-time). Todo, task, and topic operations normally also produce activity records. Activity capture alone does not authorize changes to those other records. Explicit restrictions on recording or file changes override both modes.

During active daybook use, a clear signal that the work or session is ending, pausing, being handed off, or about to restart is an immediate checkpoint in either mode. Check for eligible unsaved material in the scope that is ending and handle the save before the closing reply. Follow [Session-ending checkpoints](references/activity-capture.md#session-ending-checkpoints) for what to save and what to report.

## Required checks for a concrete operation

1. Identify the target daybook repository from the current working directory or the user's path. Do not assume a fixed absolute path.
2. Before the first concrete operation in this context, read the target repository's `README.md` and current Git status. Reuse completed setup checks only under [Reuse completed setup checks](references/operations.md#reuse-completed-setup-checks); refresh Git status before a later response's edit group, preserve unrelated changes, and reread existing records and update hashes for every write.
3. Read only the reference needed for the current operation:
   - [records.md](references/records.md) for schemas, paths, IDs, and dates.
   - [operations.md](references/operations.md) for add, update, list, activity, schedule, and day-plan workflows.
   - [todos.md](references/todos.md) for deferred separate actions, TODO registration and lists, execution, completion, and handoff to a task.
   - [topics.md](references/topics.md) for saved thematic understanding, specifications, topic lookup or consolidation, and placement under root `topics/` with optional subdirectories.
   - [activity-capture.md](references/activity-capture.md) for recording mode and timing, conversation context, URL reading and comparison, and operation outcomes.
   - [attachments.md](references/attachments.md) before retaining supplied material, generated results, or supporting files; it defines activity-first recording, durable external storage, deliberate use of attachments, temporary work files, and the extremely rare binary exception.
   - [notification.md](references/notification.md) for GitHub Actions workflow generation or email notification troubleshooting.
   - [issue-import.md](references/issue-import.md) only for an explicit request to import GitHub Issue(s).
   - [url-task-lookup.md](references/url-task-lookup.md) only for an explicit request to find daybook tasks related to a URL.
   - [waypoints.md](references/waypoints.md) for reading a named legacy waypoint or explaining the retired operations.

## Core workflow

Once an operation is requested, classify it before editing: todo, task, topic, schedule, activity, activity list or history, resumption, todo list, task list, day-plan, explicit URL-to-task lookup, explicit Issue import, notification, explanation, or explicit weekly-task maintenance. Prefer an activity for ordinary recording; choose a todo for an explicit TODO request or a concrete action clearly set aside for later under [todos.md](references/todos.md), a topic for a requested saved thematic summary, and a task for clear task registration, task consolidation, or task editing. If only that classification is unclear, choose an activity without a classification question. Doing concrete work or reaching a conclusion does not automatically create a todo, task, or topic. Resolve an existing record by its full ID/path/title before creating a new one. When record identity is ambiguous, use the available date, month, title, and links to narrow it; do not create a duplicate silently. Keep checks and edits within the requested records and information directly needed for their consistency.

For a todo operation, follow [todos.md](references/todos.md). Keep one deferred action per creation-date `todos/YYYY/YYYYMM/YYYYMMDD/` file, without requiring priority or planned dates. Read legacy `YYYY/YYYYMM/todos/` records and keep their saved paths on ordinary updates. Show open items across all dates by default; work can proceed through activities without a task. Keep completion, cancellation, and transfer to a saved task distinct, and preserve the origin links. A request to work on a specific todo includes maintaining that todo's supported remaining action and outcome; activity-only and file restrictions still take precedence.

For a topic operation, follow [topics.md](references/topics.md). Keep themes under root `topics/`, outside the year/month hierarchy. Files directly there and files in useful subdirectories are both valid; an uncertain category must not block saving. Preserve saved paths, express other relationships with links, and reorganize only within the requested scope. A topic can grow from a short finding without a task; it has no task priority, status, or planned dates. Do not automatically extract existing task bodies or relocate their attachments.

For user-provided URLs during active use, normally read the source and search relevant past activities. Keep the URL and observed result even when access fails or the relationship is uncertain. Follow the current mode for [when to save URL results](references/activity-capture.md#receive-and-read-a-url). For an explicit URL-to-task relationship request, also follow [url-task-lookup.md](references/url-task-lookup.md). Task lookup reports candidates without changing tasks and shares the common activity record. A URL alone or a request only to read or summarize a page does not start task-candidate discovery; scoped record reads needed to understand work indicated by the conversation follow topic context above. Apply task edits only within their scope under [Task completion and scope](references/operations.md#task-completion-and-scope).

For a clear task registration, requested consolidation into a task, or task edit, create a new record at `tasks/YYYY/YYYYMM/YYYYMMDD/task-YYYYMM-NNNNN-name.md` using its creation date and a monthly ID, or update an existing record at its saved path. “TODO追加” follows the todo workflow; do not create a task solely because that word was used. For consolidating accumulated findings, results, and corrections, follow [Choose how to consolidate activities](references/operations.md#choose-how-to-consolidate-activities): use a conclusion-focused account or include decision history, and ask the user before writing the task when the intended strategy is unclear. Record ideas that are not yet actionable in activities. Write `planning_state: planned` for a new task unless the user asks to keep it as Backlog; then write `planning_state: backlog`. Do not infer Backlog from missing dates, low priority, a long period, or `todo` status. A Backlog task may omit either or both planned dates; preserve that choice and do not fill dates unless the user asks to plan it. For a planned task, include both `planned_start_date` and `planned_end_date`; use the same date for a one-day plan. Use context to fill unspecified work dates; when there is no reasonable basis, use today's Asia/Tokyo date for both. Treat any assumed date as `provisional`, state the assumption in the record, and complete registration without waiting for date confirmation. Use priority `7` when unspecified. Follow [operations.md](references/operations.md) for date assumptions and its exceptions. An unbounded weekly recurring rule is exempt and must not use `planned_dates_status`; its dated occurrences use schedules. When a task becomes `done` or `cancelled`, update its status in place at its saved path; do not move it to an archive or closed folder. A task with no known `created` date may use its valid start date only during an explicitly requested migration, preserving its ID and omitting `created`. For a task list, search all current and legacy task folders and show `ID / Priority / Status / Planning state / Planned start / Planned end / Title`, grouping Backlog separately from planned tasks. Add a `Next` value for weekly tasks from `next_occurrence`; do not substitute it for the rule's planned dates or use it as a sort key.

When the user explicitly registers a weekly recurring task, keep one active task as the recurring rule and create its first dated schedule when the date and details are known. Mark it with `recurrence: weekly` and store its next date in `next_occurrence`; do not invent an end date for a recurring rule that has no planned end. Limit registration to that task and its occurrence schedule. Editing an existing weekly task does not itself request rollover. Read [records.md](references/records.md) and [operations.md](references/operations.md) for the record and explicit rollover rules.

For schedules, use `status: scheduled` or `status: cancelled`. Keep cancellation separate from the user's participation decision; cancelled events stay in the source records but are omitted from generated day-plans. Read [records.md](references/records.md) for legacy handling.

For activity recording, first follow [Record only unsaved material](references/activity-capture.md#record-only-unsaved-material). If the requested content is already saved, leave files unchanged and confirm the existing activity; a recording request alone does not require a write.

The bundled activity CLIs use `assets/daybook/scripts/record-paths.mjs` for canonical path handling. Keep this helper beside those CLIs when copying them into a target repository.

When saving new material from ongoing discussions or reports of work or investigation, create a content-specific activity file for the Asia/Tokyo date using the letter sequence in [Add an activity](references/operations.md#add-an-activity); continue an existing file for the same episode. Use the bundled activity creation and update CLIs from that procedure: new files advance past name collisions, and each update rereads current content and hash before writing. Keep one coherent episode in one activity item, including useful progress, results, and decision reasons. Keep dated detailed accounts in activities; requested topic consolidation maintains thematic understanding, while a task keeps the job's short current state and next actions with links to the topic and activities. Honor explicitly chosen task decision history under [operations.md](references/operations.md#choose-how-to-consolidate-activities). A request to work on or resume a specific task includes maintaining that task's observed progress, adopted approach, remaining work, and next actions during the work and follow-ups, unless the user limits that scope. Reading a task, proposing an approach, or recording an activity alone does not establish task-edit scope. Activity-only requests do not add todo, task, or topic edits; use [Task completion and scope](references/operations.md#task-completion-and-scope) for completion evidence.

Before retaining supplied material or generated results, follow [attachments.md](references/attachments.md). Prefer keeping the work account and necessary findings in the activity itself. For separate materials, prefer a user-designated durable location outside the daybook repository, including another Git repository, and record a stable reference. Use text attachments deliberately when preserving a supporting artifact with daybook has a concrete benefit, such as a dated evidence snapshot or a reproduction script. Preserve valuable final or human-edited results as well as originals; `workplace/` is temporary working storage, not evidence of durable retention. If long-term storage is undecided, state that in the in-scope record. Retaining a binary in daybook Git remains an extremely rare, file-specific exception. Follow [Store text attachments](references/attachments.md#store-text-attachments): reuse existing saved paths; for new material, prefer a clearly related existing task's task-id folder, otherwise use the activity's actual filename stem. A new activity attachment uses that activity's month. Do not create a task solely for storage; later task consolidation links to existing attachments without relocating or duplicating them. The reference also covers task-only and schedule-only placement. Link relatively, keep one copy of shared material, and do not copy attachments into generated day-plans.

For day-plan generation, use the target repository's updated `scripts/generate-day-plan.mjs` with its default output root so the file is written to the canonical `day-plans/YYYY/YYYYMM/day-plan-YYYYMMDD.md` path under the target repository root. It reads task and schedule records from both the new type-first layout and legacy `YYYY/YYYYMM/` folders. Use today's Asia/Tokyo date unless the user specifies another date. Set `--output-root` only when a separate staging directory is explicitly needed. The target date plus six days is the display window. The generated plan separates today's confirmed or legacy planned work, `今日の候補（予定は暫定）`, date-based task groups, and Backlog. A complete active planned provisional period containing the target date appears only as a candidate, preserving any saved action, month-only deadline, and planned week. Other provisional periods remain in date review. Active `planning_state: backlog` tasks from all months appear only in Backlog; completed/cancelled tasks stay excluded. Schedules remain date-based. Display both ends of each planned task period. Sort today's work and provisional candidates by priority and full task ID; sort dated task sections by date then priority. Priority affects ordering only, not task selection. If the user asks what to start across the daybook, combine this generator's candidate collection with open todos under [Lists and related records](references/todos.md#lists-and-related-records), showing them separately, and suggest a small first step without confirming a provisional date or changing task status. A task-specific first-step question does not require generating a plan. Regeneration overwrites the existing day-plan for that date; treat it as a generated snapshot and do not edit it as a source record. Do not reimplement selection in the skill.

For an ordinary change to an existing task's planned dates, follow [Update a task](references/operations.md#update-a-task). Read [task-date-migration.md](references/task-date-migration.md) only when the user requests migration of legacy date keys or a daybook's date schema. For a normal Backlog/planned classification update, use [Update a task](references/operations.md#update-a-task); read [task-planning-migration.md](references/task-planning-migration.md) only to adopt the planning-state field or carry out an explicit data migration.

For an explicit notification workflow generation or update, read `references/notification.md` and use its exact bundled runnable file list from [assets/daybook](assets/daybook/). Adapt repository-specific values after inspecting the target repository. Preserve existing package scripts and dependencies. Do not create a YAML-only workflow that refers to scripts absent from the target repository. Issue-intake helper scripts are a separate local setup described in [issue-import.md](references/issue-import.md); do not add them merely to install notifications.

## After editing

Validate front matter and relative links for each edited record. For tasks, also check ID and filename agreement, required priority and planned date range on newly created ordinary tasks, any present priority values (`1`–`9`), date ordering, and status checkboxes. For todos, follow [todos.md](references/todos.md) for identity, statuses, and saved task handoffs without imposing task metadata. For topics, check the creation/update dates under [topics.md](references/topics.md#content-and-dates); do not impose task metadata. Keep source email or event URLs when supplied. Record provisional task dates and their basis in the Markdown instead of presenting them as user-confirmed. Run `git diff --check` and report changed files and any remaining ambiguity. Do not commit or push unless explicitly requested.
