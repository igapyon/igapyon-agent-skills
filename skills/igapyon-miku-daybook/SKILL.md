# igapyon-miku-daybook

Manage the Markdown records in a daybook repository. The records are the source of truth; generated day-plans and GitHub notifications are derived views.

The bundled `.mjs` command-line tools run with Node.js and the files in this skill; they do not require `npm install` or `npm ci`.

The task/activity recording policy is informed by both the user's practical daybook experience and MIT OpenCourseWare's [Guidelines for Keeping a Laboratory Notebook](https://ocw.mit.edu/courses/7-16-experimental-molecular-biology-biotechnology-ii-spring-2005/b4c64ac11fc0a68466af7e025e29bf3e_lab_notebook.pdf), a course resource for *7.16 Experimental Molecular Biology: Biotechnology II* (Spring 2005). Use the material's guidance on prompt recording, observations and results, and review and next steps as supporting rationale for recording decisions. The preference for activity capture followed by task consolidation when needed is a daybook-specific judgment developed from that guidance and experience.

Keep a task's purpose, completion conditions, latest conclusion, state, and next actions with a brief history; keep dated work, ideas, trials, observations, and decision reasons in activities. Use a Waypoint when a resume point is useful. See [task and activity responsibilities](references/operations.md#task-and-activity-responsibilities) for the editing rules.

When the user combines daybook with other documents or workflows, follow their chosen division of responsibilities and authoritative sources. Keep updates within the requested scope and avoid maintaining the same work state in multiple places by default.

Unless the user specifies another style, write narrative prose in daybook records in Japanese polite form (です・ます調). Bullet items may use concise plain-form sentences or noun phrases; do not force polite endings on every bullet.

## Terminology

`task-id` (task ID) is a task's persistent identifier: its front matter `id` value in `task-YYYYMM-NNNNN` format, for example `task-202610-00014`. The same value forms the task filename's ID prefix and its attachment folder name. Use `task-id` when referring to this identifier; keep the YAML field name as `id`.

## Activation and boundaries

Initially activate only for a clear request to use daybook or perform a daybook operation, or a current repository instruction that explicitly directs use of this skill. A name mention, quoted or historical handoff text, general TODO/productivity discussion, Issue or URL reading, and questions, review, or edits about this skill alone do not initially activate record operations. Once active, continue daybook use across follow-up messages and topic changes without requiring another invocation. An explicit URL-to-task lookup, GitHub Issue import, or notification operation still requires its specific request; ordinary URL receipt follows the activity procedure below.

This skill manages daybook records, local documentation, an explicitly requested notification workflow, and the resume context for daybook-managed work. It does not automatically commit, push, create pull requests, dispatch workflows, send email, or synchronize Issues with tasks. Explicit Issue intake is a narrow exception: follow [issue-import.md](references/issue-import.md) to prepare local records, then use the bundled miku-scm skill's comment and close workflows for the intake receipt and verified intake close. The daybook request authorizes that bounded workflow, but does not bypass miku-scm's current Issue snapshot, preflight, approval, apply, and attempt-recovery requirements. Do not post comments or close Issues for an Issue read, candidate list, ordinary daybook update, or resumed import unless the user's request covers that action.

Daybook-managed work can take place in another directory or repository. Use the daybook records to identify and resume the requested work, then follow the work location's instructions and applicable workflow. Keep repository references one-way: daybook may reference the work repository, its files, and its results; do not add links, paths, or resume pointers back to daybook in the work repository's files or repository-facing text. Keep daybook-specific recording and resume context on the daybook side. See [Waypoints](references/waypoints.md) for the handoff procedure.

Weekly recurrence is maintained only for an explicit weekly-task registration or rollover request, following [operations.md](references/operations.md). Ordinary record edits and migrations do not trigger recurrence-field initialization, an additional weekly-task scan, or rollover. For rollover, process only the requested tasks; process all active weekly tasks only when the user explicitly requests that scope. The skill does not run in the background. Lists and explanations keep the records being inspected unchanged and follow the common activity capture below. Day-plan generation may write or overwrite its generated snapshot, but must not modify source task or schedule records.

## Startup and request routing

The current user's instructions take precedence over earlier conversation and repository handoff instructions. Carry forward any still-applicable operation from those sources. If an operation is specified, proceed within that scope; otherwise briefly acknowledge readiness and wait, deferring target-daybook discovery, README/Git checks, record reads, and operation-specific references.

After activation, a user-provided URL or a substantive discussion is an activity operation even without an explicit recording command. Reading this skill for a meta task does not itself establish active daybook use. Follow the user's instruction to end daybook use, stop recording, or limit file changes; do not later backfill a prohibited interval without a request.

A request to resume daybook-managed work uses the [Waypoint procedure](references/waypoints.md), even when the user does not say “Waypoint”. Adding or updating a record does not itself request resuming earlier work or reading Waypoints.

Once an operation is known, read only the records and supporting material needed for it. Use scoped filename or content searches to locate unknown records rather than loading the repository's records in advance.

During active use, at the start of each substantive topic, consider whether existing daybook records help interpret the user's meaning before forming the answer. Use the conversation and relevant records as context, including implied references without a task-id; consult further records only as needed. A topic change does not itself erase that context. Follow [topic context](references/activity-capture.md#interpret-a-new-topic-in-context) for scoped reads and uncertain connections. Keep the current request authoritative, and do not turn a speculative connection into a confirmed task association, task edit, or activity merge.

## Activity capture during active use

Activity is the common work record during active daybook use: capture meaningful conversation progress, user-provided URLs, and actual operation results, including task-only changes, lists, and investigations. Start at the first useful facts, questions, or proposals, then save at substantive response checkpoints; do not wait for a conclusion, praise, or the end of the conversation. Continue the same episode in its existing activity and preserve how the discussion developed.

Read [activity-capture.md](references/activity-capture.md) for topic context, timing, URL reading and past-activity comparison, uncertain relationships, and explicit recording restrictions. Use the existing [activity CLIs](references/operations.md#add-an-activity). Task operations normally also produce activity records; activity capture alone does not authorize task changes. Explicit instructions such as no recording, read-only, or changing only named files override the default capture.

## Required checks for a concrete operation

1. Identify the target daybook repository from the current working directory or the user's path. Do not assume a fixed absolute path.
2. Before the first concrete operation in this context, read the target repository's `README.md` and current Git status. Reuse completed setup checks only under [Reuse completed setup checks](references/operations.md#reuse-completed-setup-checks); refresh Git status before a later response's edit group, preserve unrelated changes, and reread existing records and update hashes for every write.
3. Read only the reference needed for the current operation:
   - [records.md](references/records.md) for schemas, paths, IDs, and dates.
   - [operations.md](references/operations.md) for add, update, list, activity, schedule, and day-plan workflows.
   - [activity-capture.md](references/activity-capture.md) for conversation progress, user-provided URLs, and common operation recording during active use.
   - [attachments.md](references/attachments.md) before retaining supplied material, generated results, or supporting files; it defines activity-first recording, durable external storage, deliberate use of attachments, temporary work files, and the extremely rare binary exception.
   - [notification.md](references/notification.md) for GitHub Actions workflow generation or email notification troubleshooting.
   - [issue-import.md](references/issue-import.md) only for an explicit request to import GitHub Issue(s).
   - [url-task-lookup.md](references/url-task-lookup.md) only for an explicit request to find daybook tasks related to a URL.
   - [waypoints.md](references/waypoints.md) for a request to save, list, update, or resume a Waypoint, or to resume daybook-managed work.

## Core workflow

Once an operation is requested, classify it before editing: task, schedule, activity, task list, day-plan, waypoint, explicit URL-to-task lookup, explicit Issue import, notification, explanation, or explicit weekly-task maintenance. When choosing between activity and task for a recording request, prefer an activity unless the request clearly calls for registering future work or editing a task. If only that classification is unclear, choose an activity without a classification question. Resolve an existing record by its full ID/path/title before creating a new one. When record identity is ambiguous, use the available date, month, title, and links to narrow it; do not create a duplicate silently. Keep checks and edits within the requested records and information directly needed for their consistency.

For a Waypoint operation or a request to resume daybook-managed work, follow [waypoints.md](references/waypoints.md). A waypoint is a short resume entry that points to canonical task and activity records; it does not replace them. Numbered entries are for independently resumable subwork, not a second task plan.

For user-provided URLs during active use, follow [activity-capture.md](references/activity-capture.md): normally read the source, search relevant past activities, and record the URL and observed result even when access fails or the relationship is uncertain. For an explicit URL-to-task relationship request, also follow [url-task-lookup.md](references/url-task-lookup.md). Task lookup reports candidates without changing tasks and shares the common activity record. A URL alone or a request only to read or summarize a page does not start task-candidate discovery; scoped record reads needed to understand work indicated by the conversation follow topic context above. Apply task edits only within their scope under [Task completion and scope](references/operations.md#task-completion-and-scope).

For a concrete task request, create or update a `tasks/task-YYYYMM-NNNNN-name.md` record even when the user says “TODO”. Record ideas that are not yet actionable in activities. Write `planning_state: planned` for a new task unless the user asks to keep it as Backlog; then write `planning_state: backlog`. Do not infer Backlog from missing dates, low priority, a long period, or `todo` status. A Backlog task may omit either or both planned dates; preserve that choice and do not fill dates unless the user asks to plan it. For a planned task, include both `planned_start_date` and `planned_end_date`; use the same date for a one-day plan. Use context to fill unspecified work dates; when there is no reasonable basis, use today's Asia/Tokyo date for both. Treat any assumed date as `provisional`, state the assumption in the record, and complete registration without waiting for date confirmation. Use priority `7` when unspecified. Follow [operations.md](references/operations.md) for date assumptions and its exceptions. An unbounded weekly recurring rule is exempt and must not use `planned_dates_status`; its dated occurrences use schedules. When a task becomes `done` or `cancelled`, update its status in place and keep the file in its creation-month directory; do not move it to an archive or closed folder. For a task list, show `ID / Priority / Status / Planning state / Planned start / Planned end / Title`, grouping Backlog separately from planned tasks. Add a `Next` value for weekly tasks from `next_occurrence`; do not substitute it for the rule's planned dates or use it as a sort key.

When the user explicitly registers a weekly recurring task, keep one active task as the recurring rule and create its first dated schedule when the date and details are known. Mark it with `recurrence: weekly` and store its next date in `next_occurrence`; do not invent an end date for a recurring rule that has no planned end. Limit registration to that task and its occurrence schedule. Editing an existing weekly task does not itself request rollover. Read [records.md](references/records.md) and [operations.md](references/operations.md) for the record and explicit rollover rules.

For schedules, use `status: scheduled` or `status: cancelled`. Keep cancellation separate from the user's participation decision; cancelled events stay in the source records but are omitted from generated day-plans. Read [records.md](references/records.md) for legacy handling.

For ongoing discussions and reports of work or investigation, create a content-specific activity file for the Asia/Tokyo date using the letter sequence in [Add an activity](references/operations.md#add-an-activity); continue an existing file for the same episode. Use the bundled activity creation and update CLIs from that procedure: new files advance past name collisions, and each update rereads current content and hash before writing. Keep one coherent episode in one activity item, including useful progress, results, and decision reasons. Keep detailed accounts in activities; when task editing is in scope, consolidate its current state and next actions into the task with links to the activities. A request to work on or resume a specific task includes maintaining that task's observed progress, adopted approach, remaining work, and next actions during the work and follow-ups, unless the user limits that scope. Reading a task, proposing an approach, or recording an activity alone does not establish task-edit scope. Activity-only requests do not add a task edit; use [Task completion and scope](references/operations.md#task-completion-and-scope) for completion evidence.

Before retaining supplied material or generated results, follow [attachments.md](references/attachments.md). Prefer keeping the work account and necessary findings in the activity itself. For separate materials, prefer a user-designated durable location outside the daybook repository, including another Git repository, and record a stable reference. Use text attachments deliberately when preserving a supporting artifact with daybook has a concrete benefit, such as a dated evidence snapshot or a reproduction script. Preserve valuable final or human-edited results as well as originals; `workplace/` is temporary working storage, not evidence of durable retention. If long-term storage is undecided, state that in the in-scope record. Retaining a binary in daybook Git remains an extremely rare, file-specific exception. New attachments arising from an activity use that activity's month; task-related material uses `attachments/<task-id>/` even when the task was created in another month. Keep existing attachments at their saved paths when updating or referencing them. Follow the reference for activity-only, task-only, and schedule-only placement. Link relatively, keep one copy of shared material, and do not copy attachments into generated day-plans.

For day-plan generation, use the target repository's updated `scripts/generate-day-plan.mjs` with its default output root so the file is written to the canonical `YYYY/YYYYMM/day-plan/day-plan-YYYYMMDD.md` path under the target repository root. Use today's Asia/Tokyo date unless the user specifies another date. Set `--output-root` only when a separate staging directory is explicitly needed. The target date plus six days is the display window. The generated plan separates today's confirmed or legacy planned work, `今日の候補（予定は暫定）`, date-based task groups, and Backlog. A complete active planned provisional period containing the target date appears only as a candidate, preserving any saved action, month-only deadline, and planned week. Other provisional periods remain in date review. Active `planning_state: backlog` tasks from all months appear only in Backlog; completed/cancelled tasks stay excluded. Schedules remain date-based. Display both ends of each planned task period. Sort today's work and provisional candidates by priority and full task ID; sort dated task sections by date then priority. Priority affects ordering only, not task selection. If the user asks what to start across the daybook, use this generator's candidate collection and suggest a small first step without confirming a provisional date or changing task status. A task-specific first-step question does not require generating a plan. Regeneration overwrites the existing day-plan for that date; treat it as a generated snapshot and do not edit it as a source record. Do not reimplement selection in the skill.

For an ordinary change to an existing task's planned dates, follow [Update a task](references/operations.md#update-a-task). Read [task-date-migration.md](references/task-date-migration.md) only when the user requests migration of legacy date keys or a daybook's date schema. For a normal Backlog/planned classification update, use [Update a task](references/operations.md#update-a-task); read [task-planning-migration.md](references/task-planning-migration.md) only to adopt the planning-state field or carry out an explicit data migration.

For an explicit notification workflow generation or update, read `references/notification.md` and use its exact bundled runnable file list from [assets/daybook](assets/daybook/). Adapt repository-specific values after inspecting the target repository. Preserve existing package scripts and dependencies. Do not create a YAML-only workflow that refers to scripts absent from the target repository. Issue-intake helper scripts are a separate local setup described in [issue-import.md](references/issue-import.md); do not add them merely to install notifications.

## After editing

Validate front matter, ID and filename agreement, required priority and planned date range on newly created ordinary tasks, any present priority values (`1`–`9`), date ordering, status checkboxes, and relative links. Keep source email or event URLs when supplied. Record provisional dates and their basis in the Markdown instead of presenting them as user-confirmed. Run `git diff --check` and report changed files and any remaining ambiguity. Do not commit or push unless explicitly requested.
