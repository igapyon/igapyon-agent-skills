# igapyon-skill-compactor

## Overview

This skill helps redesign oversized Agent Skill systems for runtime token
efficiency, then compacts the Agent Skills themselves when that is the right
final step. It preserves trigger intent, behavior, validation surface, and
progressive-disclosure structure.

Use it as a maintenance and design workflow for existing Agent Skills and
skill-adjacent workflows, not as a generic editor.
This skill itself does not need to be unusually compact. Its own instructions
should remain compact enough to load responsibly, but complete enough to prevent
unsafe or behavior-changing compaction.

## Core Principles

- Compaction is not shortening; it is runtime token-efficiency design.
- Preserve behavior before reducing tokens.
- Move meaning instead of erasing meaning.
- Discuss unclear boundaries with the human before editing.
- Separate prototype/R&D cost from stable runtime cost.
- Split skills when one skill contains multiple independent jobs.
- Move deterministic or external work out of skills when tools, scripts, or MCP fit better.
- Keep trigger intent precise.
- Prefer progressive disclosure over always-loaded detail.
- Treat context debt like technical debt.
- Do not over-compact this skill's own judgment rules; they are safeguards.

Read [references/system/design-philosophy.md](references/system/design-philosophy.md) when
the compaction target is ambiguous, risky, architectural, or may require
splitting skills/tools/workflows.

## Compacting Workflow

1. Frame the repeated runtime task with the human when needed.
2. Read target skills early when useful for understanding, but avoid editing
   before system boundaries and placement choices are clear.
3. Inventory skills, prompts, templates, tools, scripts, MCP, changing inputs,
   stable context, required outputs, and judgment-heavy steps.
4. Decide the right placement before editing: human procedure, split skill,
   `SKILL.md`, references, distilled summaries, scripts, assets, MCP/tooling,
   stable prefix material, output constraints, reasoning-depth reduction,
   deletion, or no change.
5. Read or reread target skill directories in detail and map each skill
   contract: triggers, non-triggers, behavior, output style, references,
   validation, safety constraints, and separable responsibilities.
6. Before risky compaction, add or update representative prompt tests for
   activation, non-activation, behavior, reference routing, and ask-human cases;
   run a baseline when feasible.
7. Decide whether to compact, split, toolize, use MCP, constrain output, reduce
   reasoning demand, or leave the skill as-is.
8. Rewrite Agent Skills for progressive disclosure while preserving trigger
   behavior and avoiding accidental overlap or double-triggering.
9. Validate against the same prompt tests, representative requests, reference
   reachability, available validators, and expected repeated runtime
   input/output/context reduction.

## Compaction Rules

- Preserve meaning before reducing size.
- Prefer deletion of generic explanation over deletion of task-specific rules.
- Prefer moving detailed examples to references over leaving them in `SKILL.md`.
- Use `distilled/` for human- or agent-approved distilled Markdown derived from
  larger source materials, and keep it updated when sources or decisions change.
- Keep frontmatter `description` precise because it is part of activation.
- Keep `SKILL.md` short enough to read quickly; split when sections become long.
- Do not add README, changelog, install guide, or auxiliary documentation
  unless the user explicitly requires human-facing maintenance context; do not
  let such files become runtime prompt material.
- Do not rewrite a skill into a different workflow unless the user asks.

## Output

When editing a skill, summarize:

- system-level decisions made with the human
- whether the solution used compaction, splitting, toolization, MCP, output constraints, or no change
- pre-work and post-work checklist highlights from `references/system/token-efficiency-techniques.md`
- how repeated runtime input/output/context load is expected to change
- what stayed in `SKILL.md`
- what moved to references, scripts, or assets
- what was deleted and why
- prompt-test baseline and post-change validation performed
- remaining risks or follow-up checks
