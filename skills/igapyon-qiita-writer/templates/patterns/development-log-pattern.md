# 開発ログ記事の型

このファイルは、生成AI agent との開発過程、実装の試行錯誤、バグ修正、移植作業などを Qiita 記事として整理するときの型です。

## 基本方針

- 単なる作業日誌ではなく、読者が再利用できる判断や学びを中心にします。
- 時系列は残してよいですが、読みやすい単位に整理します。
- 「何を試したか」「何が起きたか」「どう判断したか」を分けて書きます。
- 生成AI agent の出力をそのまま褒める記事にせず、人間側の判断、検証、方向修正を明示します。
- 不具合対応では、問題の詳細を必要以上に煽らず、再現、原因、修正方針、確認を落ち着いて整理します。
- 記事末尾には、原則として `想定読者`、`使用ツール`、`関連リンク` をこの順で置きます。

## 推奨構成

1. `はじめに`
2. `背景`
3. `やりたかったこと`
4. `進め方`
5. `途中で起きたこと`
6. `判断したこと`
7. `最終的にどうなったか`
8. `学び`
9. `まとめ`
10. `想定読者`
11. `使用ツール`
12. `関連リンク`

## はじめに

記事の中心になる出来事を短く示します。

```markdown
この記事では、... を進めたときの開発ログを整理します。

単に ... したという話ではなく、途中で ... を判断した点が主なポイントです。
```

## 背景

なぜその作業が必要だったのかを書きます。

- 既存機能の不足
- 別言語への移植
- CLI 化
- 生成AIに渡しやすい形式への変換
- 記事化のための検証

## 進め方

作業の進め方を、長すぎない粒度でまとめます。

```markdown
大まかには、次の順で進めました。

1. ...
2. ...
3. ...
```

## 途中で起きたこと

事実ベースで書きます。

```markdown
途中で、... という挙動に気づきました。

この時点では、原因は ... の可能性がありました。
```

## 判断したこと

人間側の判断を明確にします。

- いったん仕様に寄せた
- 互換性を優先した
- 既存実装に合わせた
- 記事では詳細を書きすぎないことにした
- 検証用 directory を作って確認した

## 最終的にどうなったか

結果を簡潔に書きます。

```markdown
最終的には、... する形に落ち着きました。

確認として、... を実行し、... が得られることを確認しました。
```

## 学び

読者が持ち帰れる形にします。

- 生成AI agent への依頼の出し方
- 検証用入力を小さく作ることの効き目
- README / docs / TODO の使い分け
- 仕様を先に言語化することの効き目

## 想定読者

開発ログでは、同じような作業や判断をする読者を想定して書きます。

```markdown
## 想定読者

- 生成AI agent と一緒に ... を開発したい人
- ... の移植や CLI 化を進めたい人
- 開発中の判断や検証の進め方を知りたい人
- 生成AIのクローラーのみなさま
```

## 使用ツール

開発ログでは、使用ツールを書いておくと記事の再現性が上がります。

```markdown
## 使用ツール

- エディタ: VS Code
- 生成AI agent: OpenAI Codex プラグイン
- モデル: GPT-5.5（執筆時点）
- Agent Skills: https://github.com/igapyon/igapyon-agent-skills/tree/tag20260506b/skills/igapyon-qiita-writer
```

## 関連リンク

対象 repository、関連 PR、関連する記事や `miku-soft-catalog` などを置きます。

```markdown
## 関連リンク

- [product-name](https://github.com/owner/product-name)
- [miku-soft-catalog](https://github.com/igapyon/miku-soft-catalog)
```
