# Release Automation Review

Use this review note for miku-soft repositories that build, package, or attach
release artifacts through local scripts or GitHub Actions.

Release automation is a frequent source of implementation gaps because miku-soft
repositories often have more than one artifact role: npm package, single-file
Web App, single-file CLI runtime, Java jar, source archive, Agent Skills bundle,
MCP server package, docs, and generated indexes.

## Classification

Apply this review when the target repository has any of these:

- local release build scripts
- GitHub Actions release workflow
- `v*` tag based release assets
- npm package publication or `npm pack`
- single-file Web App artifact
- single-file Node.js CLI runtime artifact
- Java jar or distribution zip
- Agent Skills bundle or bundle zip
- MCP package or server distribution artifact

## Artifact Role Checks

Check these points:

- each release artifact has a clear role, such as Web App, CLI runtime, source
  archive, Java runtime, npm package, skill bundle, or docs bundle
- artifact names include the product name and version where practical
- release assets do not confuse npm package tarballs with single-file CLI
  runtime artifacts
- source archives are separate from runtime artifacts
- generated indexes, docs, and metadata are either regenerated by the release
  build or explicitly treated as prebuilt inputs
- README and release workflow agree on which artifacts are produced
- release assets are built from the release tag, not an unrelated branch tip

## Version and Tag Checks

Check these points:

- newly created miku-soft repositories normally start at version `0.5.0`
- initial package, Maven, skill bundle, runtime artifact, and release metadata
  use `0.5.0` consistently when the repository is newly created
- normal miku-soft project versions do not use a `-SNAPSHOT` suffix unless the
  repository documents a specific reason
- `package.json`, Maven `pom.xml`, skill bundle metadata, or other version
  sources are checked against the release tag
- accepted tag suffix rules are explicit when patch suffix tags such as
  `v0.5.0.1` are allowed
- release asset filenames use the tag version consistently
- `--version` output, runtime embedded version, package metadata, and release
  asset names agree
- workflows reject unrelated tags rather than producing mislabeled artifacts
- generated build dates use the intended timezone or an explicit supplied date
  when release artifacts display dates

## Workflow Trigger Checks

Check these points:

- Node.js / TypeScript main application release asset workflows normally
  trigger on `push` tags matching `v*`
- GitHub Release `published` is not the standard trigger for Node main app
  release assets; require a repository-specific reason when it is used
- `workflow_dispatch` is optional for Node main app release assets; when used,
  it requires an explicit `tag_name` input and only proceeds for `v*` tags
- CI baseline workflows are not confused with release asset workflows
- pull-request and ordinary-push CI baseline workflows are not created as part
  of release asset automation unless explicitly requested
- publish workflows, such as `npm publish`, are separate from release asset
  attachment unless the repository intentionally combines them
- workflow permissions are scoped to the needed operation
- checkout uses the release tag or manually supplied tag
- workflow steps fail early when required artifacts or version checks are
  missing

## Build and Smoke Checks

Check these points:

- release workflow runs the repository's documented build command
- tests or focused smoke checks run before assets are staged
- Node main app release workflows delegate build and smoke to local `npm scripts`
  or `scripts/*.mjs`; version checks and release asset staging may stay in the
  workflow when they only adapt local build outputs into versioned release asset
  names
- CLI runtime assets are smoke-tested with at least `--version` and `--help`
- Java runtime assets are smoke-tested with equivalent metadata commands when
  available
- Agent Skills bundles have contents tests and isolated bundle smoke tests
- Single-file Web App artifacts are checked for unreplaced placeholders,
  missing local runtime, and unintended remote dependencies
- MCP server packages have at least contract or startup smoke checks for the
  intended transport
- release staging directory is recreated cleanly for each run

## Upload and Publication Checks

Check these points:

- workflows upload only prepared release assets, not broad repository source
  zips or accidental build directories
- asset glob patterns cannot pick up stale artifacts from previous builds
- artifact upload names match README and downstream expectations
- release upload steps fail when expected files are missing
- npm publication, Maven publication, GitHub Release asset upload, and skill
  bundle zip upload are treated as different operations
- human-owned operations such as creating GitHub releases, pushing tags, or
  publishing packages are not performed by the skill workflow unless explicitly
  requested outside Review mode

## Local Reproducibility Checks

Check these points:

- release artifacts can be built locally with documented commands
- required runtime artifacts are either built in the repository or received at
  documented paths before packaging
- release scripts do not require network access except for explicit dependency
  installation, upload, or publication steps
- local build output is deterministic enough for review when practical
- temporary and staging directories are ignored or cleaned
- `workplace/` contents are not packaged into release artifacts

## Severity Guidance

Use this severity guidance during Review mode:

- Critical: release automation uploads private local files, `workplace/`
  contents, secrets, or unintended artifacts.
- High: release assets are built from the wrong git ref or an unchecked branch
  tip instead of the release tag.
- High: tag version, package version, runtime `--version`, and asset filenames
  can diverge without workflow failure.
- High: a release workflow uploads `npm pack` output where the documented asset
  role is a single-file CLI runtime, or vice versa.
- High: skill bundle or runtime release assets are missing required runtime
  files but the workflow still succeeds.
- Medium: a newly created miku-soft repository starts from a version other than
  `0.5.0`, or its initial package, Maven, skill, runtime, and release metadata
  disagree, without documenting the reason.
- Medium: a normal miku-soft project version uses `-SNAPSHOT` in package,
  Maven, skill, runtime, or release metadata without a clear
  repository-specific reason.
- Medium: release workflow lacks smoke checks for generated runtime artifacts.
- Medium: generated Web App release artifacts can contain unreplaced build
  placeholders or wrong build dates.
- Medium: workflow trigger, permissions, or upload glob patterns are broader
  than the documented release operation.
- Medium: README and workflow disagree about artifact names or release steps.
- Low: minor naming, docs, or staging-directory cleanup issues make release
  review harder without changing produced artifacts.

## Review Output

When this review applies, include a short classification before findings:

```text
Release Automation Review

Release shape: GitHub Release asset / npm package / Java distribution / skill bundle / MCP package
Trigger: tag push / release published / workflow_dispatch / manual local
Version source: package.json / pom.xml / skill metadata / tag
Artifacts: Web App / CLI runtime / jar / source archive / skill zip / docs
Smoke checks: present / missing / partial
```

Then report findings in severity order. Do not edit files during Review mode
unless the user explicitly asks to switch from review to maintenance work.
