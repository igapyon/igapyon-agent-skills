# Single-file Web App Review

Use this review note for miku-soft `11 Web App` repositories, or historical
combined repositories, that provide a browser-based single-file Web App.

This review perspective is specific to the miku-soft series. A normal Web App
review may accept server calls, CDN dependencies, or remote assets, but a
miku-soft Single-file Web App is expected to work as a local-first, offline
artifact.

## Classification

Apply this review when the target repository or artifact has this shape:

- layer: `11 Web App`, or historical combined `10` / `11` repository
- UI shape: Single-file Web App
- distribution artifact: one HTML file, or a build process that produces one
  HTML file
- expected use: open locally in a browser without installing or starting a
  server

If the repository also has a CLI, review the CLI separately. The Web App review
focuses on the browser artifact and the browser execution contract.

## Core Contract

A miku-soft Single-file Web App must satisfy these principles:

- It is actually usable as a single-file Web App.
- It works offline.
- During normal operation, it does not communicate over the network.
- It does not depend on remote CDN scripts, stylesheets, fonts, images, WASM,
  workers, or APIs.
- User-selected local input files are processed locally in the browser.
- Conversion, preview, diagnostics, and download flows complete in the browser.

Treat the offline and no-network behavior as product contract, not as an
optional implementation preference.

## Review Checks

Check the source, build output, and documentation as appropriate:

- The produced HTML can be opened directly from the local filesystem.
- The produced HTML includes the runtime it needs, rather than loading runtime
  code from remote URLs.
- Production HTML does not contain remote `<script src=...>` dependencies.
- Production HTML does not contain remote `<link href=...>` stylesheet or font
  dependencies.
- Production code does not call remote APIs during normal load, conversion,
  preview, diagnostics, or download operations.
- Production code does not upload local file content or derived artifacts.
- Remote images, fonts, CSS imports, Web Workers, WASM, or dynamic imports are
  absent unless explicitly documented as non-default optional behavior.
- README and docs describe local/offline use consistently with the actual
  artifact.
- Tests or smoke checks cover direct local opening or equivalent offline
  behavior when the repository provides browser verification.

## Source and Distribution Checks

Several miku-soft Web App references keep editable source HTML and generated
distribution HTML separate. Review the repository's actual naming convention,
but check for the same role split:

- source HTML, such as `index-src.html` or `<product>-src.html`, is the file
  humans edit
- distribution HTML, such as `index.html` or `<product>.html`, is generated
  from source HTML and local source files
- generated HTML is not hand-edited when the repository documents a build path
- build scripts inline or otherwise bundle local JavaScript, CSS, shared
  components, and vendor files needed by the app
- README names the published single-file artifact clearly
- release or distribution instructions do not confuse the source HTML with the
  generated single-file artifact

If the production artifact still references many local files, classify whether
the repository intentionally uses a multi-file development page, or whether the
single-file build is missing or stale.

## Build Date Checks

Several miku-soft Single-file Web Apps show an `Updated` or generated date in
`index.html` or `<product>.html`. Treat this as part of the generated artifact
quality because users use it to identify the shipped local file.

Check these points:

- source HTML uses an explicit placeholder such as `{{BUILD_DATE}}` when the
  date is generated by the build
- generated distribution HTML has the placeholder replaced
- the date format is stable, normally `YYYY-MM-DD`
- the intended timezone is explicit in the build script or documentation when
  the date is generated automatically
- CI, release, and local builds use the same intended timezone
- generated date logic does not silently depend on the host machine timezone
  when the project expects a Japan-local date
- tests or simple build checks fail if `{{BUILD_DATE}}` remains in production
  HTML
- generated dates are reviewed when release artifacts are built near midnight
  UTC or Japan time

For miku-soft repositories maintained on a Japan-local release cadence, prefer
an explicit `Asia/Tokyo` date calculation or an explicitly supplied build date
over plain `new Date()` plus `getFullYear()`, `getMonth()`, and `getDate()`.
Those local-time getters depend on the executing environment. In GitHub Actions
or other CI environments, that often means UTC, which can produce a date one day
behind or ahead of the intended Japan date.

If the repository intentionally uses UTC, that is acceptable only when the UI
label, release process, and documentation make the UTC convention clear.

## UI and CLI Alignment Checks

Many miku-soft Web Apps also provide a Node.js CLI. The Web UI and CLI do not
need identical interaction models, but they should expose the same product
semantics where they overlap.

Check these points when a CLI exists:

- browser UI and CLI call the same core logic or a clearly shared product
  contract
- defaults that affect conversion meaning are aligned, or documented as
  intentionally different
- output modes, diagnostics, warnings, summaries, and artifact roles use the
  same vocabulary
- browser-only adapters are limited to browser concerns such as File API,
  download, DOM preview, local encoding support, and UI state
- Node-only adapters are limited to file I/O, stdout/stderr, process exit
  codes, filesystem paths, and batch execution
- CLI behavior is not used as an excuse to weaken the browser offline contract

When the UI and CLI diverge, review whether the divergence comes from a real
runtime constraint or from duplicated product logic drifting apart.

## Local Data and Feedback Checks

The miku-soft references treat real local data findings as reusable product
knowledge. Review whether the repository has a way to turn local discoveries
into durable checks without committing private data.

Check these points:

- private local samples stay under ignored local work areas such as
  `workplace/` or product-specific local-data directories
- reduced fixtures, golden outputs, or synthetic samples are added when a local
  data issue reveals a product behavior that should stay fixed
- diagnostics make unsupported, lossy, fallback, skipped, or approximate
  behavior visible to the user
- README, docs, TODO, or tests are updated when local data review changes the
  known product boundary
- generated outputs used for review are deterministic enough to compare in
  diffs

Do not require private customer or personal files to be committed just to prove
coverage. Prefer minimized fixtures and documented reproduction steps.

## lht-cmn and Vendor Checks

miku-soft Single-file Web Apps use `lht-cmn/` in principle. Treat `lht-cmn/`
as the standard shared component layer for Web UI unless the repository
documents a clear product-specific reason to differ.

Some apps also bundle local vendor code. This is acceptable when the code
remains local and traceable.

Check these points:

- Web UI uses `lht-cmn/` as the standard shared component layer
- UI controls, layout conventions, and basic interaction patterns follow the
  local `lht-cmn/` components where they fit
- page-local UI components are added only for product-specific interactions
  that `lht-cmn/` does not reasonably cover
- shared UI components are local files, not remote UI dependencies
- vendor files required at runtime are vendored or bundled into the production
  artifact
- vendor refresh scripts, if present, are development or maintenance tools and
  are not required during normal browser use
- licenses, notices, or third-party documentation are present when local vendor
  code is distributed
- page-specific UI code stays thin over shared components and product core

Remote project links in README, metadata, Open Graph tags, or normal anchor
elements are not by themselves network violations. They become review findings
only when normal app operation depends on loading or calling them.

If a miku-soft Single-file Web App invents a separate page-local component
system while `lht-cmn/` would reasonably fit, report that as a maintainability
and series-consistency concern.

## Responsiveness Checks

A miku-soft Single-file Web App should remain usable while processing local
files in the browser. Review responsiveness as part of the local-first product
contract, especially for converter, preview, diagnostics, and download flows.

Check these points:

- initial page load is not delayed by unnecessary heavy work before the user
  selects a file
- file loading, conversion, preview generation, diagnostics, and download
  preparation show clear progress or busy state when they may take noticeable
  time
- long-running processing does not leave primary controls in an ambiguous
  clickable state
- the UI recovers predictably after parse errors, unsupported inputs, size
  limits, or conversion failures
- large-file handling has a documented or tested limit, warning, or failure
  behavior
- expensive preview rendering is staged, deferred, cached, or otherwise kept
  from blocking basic result inspection when practical
- repeated operations on the same input do not accumulate stale state,
  duplicate event handlers, leaked object URLs, or runaway memory growth
- smoke or UI tests cover at least one representative real-size or synthetic
  large input when performance risk is material

Do not require deep performance optimization for every small tool. Focus on
whether the app stays understandable and recoverable under realistic local
input sizes for its domain.

## Mainstream Flow Discoverability Checks

A miku-soft Single-file Web App should make the main user flow naturally
discoverable. For most Web UI products in the series, the primary path is a
short local workflow such as load, inspect, convert or preview, then save or
download.

Check these points:

- the first screen makes the primary local action obvious, normally selecting
  or dropping a local file
- primary controls appear in the order users need them for the mainstream flow
- the next available action becomes clear after each state change, such as file
  loaded, conversion completed, diagnostics available, or output ready
- optional modes and advanced settings do not obscure the normal path
- labels use the product's artifact vocabulary, not generic UI wording that
  hides what will be produced
- diagnostics, preview, and download controls are visible at the point where
  users need them
- empty, loading, success, warning, and failure states keep the user oriented
  without requiring external instructions
- README and in-app wording describe the same mainstream flow

Do not require an explanatory landing page. If a page or introduction exists,
review whether it helps the mainstream workflow or gets in the way of loading,
inspecting, converting, previewing, or downloading local artifacts.

## Allowed Exceptions

These cases may be acceptable when they are explicit and non-default:

- A user intentionally enters or selects a URL as an input source.
- A user clicks a normal documentation or project link and the browser
  navigates away.
- Development-only dependencies used by a dev server or test harness.
- An optional update check that is disabled by default and clearly documented.

Do not treat development-only network use as acceptable if the same dependency
is present in the production single-file artifact.

## Severity Guidance

Use this severity guidance during Review mode:

- Critical: local input file contents or derived artifacts are sent to a remote
  service during normal operation.
- High: the production Web App requires network access, CDN code, remote
  styles, remote fonts, remote WASM, or remote APIs for normal operation.
- High: the release artifact is not actually usable as a single local HTML file.
- Medium: generated `Updated` or build dates can shift by timezone because the
  build depends on the host local timezone without documenting that convention.
- Medium: production HTML still contains an unreplaced build date placeholder.
- Medium: Web UI avoids `lht-cmn/` without a clear product-specific reason,
  making the app harder to maintain consistently with the series.
- Medium: realistic local inputs can make the UI appear stuck because progress,
  busy state, error recovery, or size-limit behavior is missing.
- Medium: the primary load, inspect, convert, preview, or download path is hard
  to discover because advanced controls, unclear labels, or weak state
  transitions obscure the mainstream workflow.
- Medium: documentation claims offline or single-file behavior that the
  artifact does not clearly satisfy.
- Medium: offline behavior is intended but not covered by any smoke test or
  repeatable verification path in a mature repository.
- Low: minor documentation wording or release naming makes the single-file
  contract harder to recognize, without changing behavior.

## Review Output

When this review applies, include a short classification before findings:

```text
Single-file Web App Review

Layer: 11 Web App
UI shape: Single-file Web App
Offline contract: required
Network policy: no network during normal operation
Distribution artifact: single local HTML file
```

Then report findings in severity order. Do not edit files during Review mode
unless the user explicitly asks to switch from review to maintenance work.
