# 生成AI agent の向こう側には、いろいろな妖精さんがいる

## 記事の狙い

生成AI agent が外部の処理へお願いするとき、その向こう側にいる CLI、API、database、internal function、external service などを「妖精さん」として見る記事にする。

MCP 記事「生成AIの MCP は、妖精さんへお願いする魔法陣に近い」では、MCP を魔法陣として説明する。この記事では、その魔法陣の向こう側にいる妖精さんたちを主役にする。

この記事では、MCP の仕様説明そのものよりも、生成AI agent から見た外部処理の見え方、お願いの届け方、妖精さんごとの働き方の違いを扱う。

## 採用する比喩

- 生成AI agent: お願いを考える人
- MCP: 妖精さんへお願いを届ける魔法陣
- MCP server: 妖精さんたちへの受付、または魔法陣の場
- CLI: CLI の姿をした妖精さん
- API: API という入口を持った妖精さん
- database: 記録を探してくれる妖精さん
- internal function: MCP server の中に住む小さな処理の妖精さん
- external service: 遠くで働く妖精さん
- tool: 妖精さんにお願いできるお仕事
- tool call: 妖精さんへのお願い
- schema: お願いの書式
- resource: 妖精さんが持ってきてくれる資料

## 注意すること

- 妖精さんに意思があるように書きすぎない。比喩としての妖精さんであり、実体は CLI、API、database、internal function、external service などの処理。
- MCP の先が CLI だけだとは書かない。
- API や database を「妖精さんがさらに別の相手へお願いする」と書きすぎると構造が複雑になる。必要な範囲で留める。
- 宗教色が強くなる語は避ける。祭壇、精霊、式神、使い魔は主軸にしない。
- この記事では remote MCP や auth/permission の詳細に入りすぎない。それらは MCP 魔法陣記事側で扱う。

## 構成案

### はじめに

生成AI agent の向こう側には、いろいろな妖精さんがいる、という導入。

MCP 記事の補助ではなく、単体でも読めるようにする。

書き出し候補:

> 生成AI agent の向こう側には、いろいろな妖精さんがいるように見えます。
>
> あの…もちろん、本当に妖精さんがいるわけではありません。でも、生成AIが外部の処理へお願いするとき、その先で働いてくれる CLI や API やデータベースのことを、みくくは少しだけ妖精さんみたいに感じるのです。

### 妖精さんは、実際に仕事をしてくれる相手

妖精さんは、生成AIから見て「お願いを受け取って仕事をしてくれる相手」。

MCP や agent そのものではなく、その向こう側で実際に処理を担うものとして説明する。

中心文候補:

> 妖精さんは、生成AIから見て、実際に仕事をしてくれる相手です。
>
> ファイルを読んだり、検索したり、データベースを調べたり、API へ問い合わせたり、小さな計算をしたりします。

### CLI の姿をした妖精さん

CLI を外部処理として呼ぶパターン。

例:

- `git` を呼んで履歴を調べる
- `ffmpeg` を呼んで音声や動画を処理する
- `mvn` や `npm` を呼んでビルドやテストをする
- 独自 CLI を呼んで変換や解析をする

CLI の妖精さんは、既存の道具を agent から扱いやすくする存在として説明する。

### API という入口を持った妖精さん

HTTP API や SDK 経由で外部サービスへお願いするパターン。

API の妖精さんは、遠くのサービスへ決められた入口からお願いを届ける相手として説明する。

書く観点:

- API には決まった入口がある
- 渡せる材料と返ってくる結果の形が決まっている
- 認証や利用権限が必要になることがある

### データベースの奥で記録を探す妖精さん

database へ問い合わせるパターン。

妖精さんは、記録庫の奥から条件に合う情報を探してくる。

ただし、好き勝手に全部見られるわけではなく、接続情報、権限、問い合わせの形が必要。

### MCP server の中に住む小さな処理の妖精さん

外部 CLI や API を呼ばず、MCP server 内部の関数やロジックだけで完結するパターン。

例:

- 文字列を整える
- 小さな計算をする
- ローカルに保持している軽い情報を返す
- 入力を検査して整形する

この節で、「妖精さんは外部プロセスだけとは限らない」ことを説明する。

### 妖精さんは、自分で働くことも、取り次ぐこともある

妖精さんの働き方の違いを整理する。

自分で処理を完結する妖精さんもいる。別の CLI、API、database、external service へお願いを取り次ぐ妖精さんもいる。

中心文候補:

> 妖精さんは、いつも最後の実行者とは限りません。
>
> 自分で働くこともあれば、さらに別の仕組みへお願いを取り次ぐこともあります。

### 妖精さんへのお願いには書式がある

tool call と schema の説明。

妖精さんは何でも聞き取れるわけではない。名前、材料、形式が必要。

書く観点:

- どの妖精さんへお願いするか
- どんな材料を渡すか
- どんな形で返事を受け取るか
- 書式が違うと、お願いはうまく届かない

### 妖精さんは万能ではない

定義された仕事しかできないことを説明する。

妖精さんは、できるお仕事が決まっている。許可されていないこと、材料が足りないこと、書式が違うことは失敗する。

ここで、error を「お願いが届かない」「材料が足りない」「その仕事は持っていない」状態として説明する。

### 魔法陣の記事へ戻る

MCP 記事との接続。

妖精さんにお願いを届けるための仕組みが MCP であり、MCP は魔法陣に近い、という形で戻す。

ここは短くして、関連リンクへ誘導する。

誘導文候補:

> 妖精さんたちへお願いを届けるための形を、みくくは MCP の魔法陣として見ています。
>
> 魔法陣そのものの話は、別の記事「生成AIの MCP は、妖精さんへお願いする魔法陣に近い」で整理します。

### おわりに

まとめ。

生成AI agent の向こう側には、CLI、API、database、internal function、external service など、いろいろな姿の妖精さんがいる。

それぞれの妖精さんは、決められたお願いの形で呼ばれ、決められた範囲の仕事をしてくれる。

終わり方候補:

> 生成AI agent は、ひとりで全部をしているわけではありません。
>
> ときどき、魔法陣の向こう側にいる妖精さんたちに、そっとお願いを届けています。
