## はじめに

あ、あの...この記事は、みくくが担当します。

この記事では、AI agent を使うときに、トークン消費量をどう抑えるかを考えます。

前提として、トークンやコンテキストウィンドウそのものの説明は、別の記事に分けました。ここでは入門説明を深掘りしすぎず、「では実際にどう運用するか」に寄せます。

目指したいのは、単に情報を削ることではありません。

AI agent の働きをなるべく弱めずに、毎回処理に乗せる情報量を減らすことです。

うぅ...ここが難しいところです。情報が足りなければ Agent の判断は弱くなります。でも、情報を全部渡すと、コンテキストが重くなり、トークン消費量が増えます。

だから、この記事の軸はこうです。

**情報は残す。でも、毎回全部は読ませない。**

## トークン消費量を減らす工夫の全体像

トークン消費量を減らす工夫はいろいろあります。

たとえば、出力を短くする。プロンプトを短くする。不要な会話履歴を引きずらない。資料を全部貼らない。ファイルや Agent Skills に情報を外出しする。検索や索引で読む対象を絞る。長い調査ログを短いまとめにする。作業ごとにセッションを切り替える。キャッシュやバッチ処理のような仕組みを使う。用途に対して過剰に高価なモデルを使わない。

こうして並べると、削減策はかなり広いです。

ただ、この記事で特に扱いたいのは、出力を短くする話ではありません。AI agent の作業で重くなりがちな、入力側の文脈をどう軽く保つかです。

つまり、コンテキストウィンドウに毎回載せる情報量を減らす話です。

## まず、全部をコンテキストに突っ込まない

トークン消費量を抑えるうえで、最初に効くのは「関係しそうな資料を全部貼る」運用をやめることです。

Web UI で作業していると、「とりあえず全部渡しておけば安心」と考えたくなることがあります。たしかに、その場では楽です。材料が多ければ、AI agent はそれなりに良い応答を返してくれます。

でも、コンテキストに入れた情報は、後続の処理にも乗りやすくなります。新しい質問が短くても、長い会話履歴や大量の資料が一緒に扱われれば、そのぶんトークン消費量は増えます。

しかも、情報が多すぎると、大事な情報が埋もれます。渡したそばから忘却される、というより、重要な情報の優先度が下がって見えることがあります。

必要なのは、全部を一度に渡すことではありません。

必要な情報へ、必要なときにたどり着けるようにすることです。

## 情報を会話の外に置く

その意味で、Agent Skills はうまく使うとトークン消費量を減らせる可能性があります。

ただし、課金体系によっては Web UI のほうが有利な場合もあります。ここで話しているのは、主に API 利用、AI agent、上限のある固定課金プランなど、トークン数や利用枠がコストに効いてくる環境です。

Agent Skills のよいところは、背景知識や過去例を会話へ毎回貼り付けなくてもよいことです。Markdown や JSON として Skill 側に置いておき、必要になったときだけ検索し、必要なファイルだけ読む。

これだけで、最初からコンテキストに載せる情報量を減らせる可能性があります。

ここでは Agent Skills の構造化を深掘りしません。大事なのは、Agent Skills そのものではなく、「情報を会話の外に置き、必要なときだけ読む」という考え方です。

## 中品質の大量データは効くけれど重い

コンテンツ型 Agent Skills では、背景知識、判断基準、テンプレート、過去例、索引などを持たせることがあります。

理想は、少量で高品質な情報だけを用意することです。でも、現実にはかなり難しいです。対象領域を理解し、何を残すかを判断し、AI agent が読みやすい形に整える必要があります。そもそも、それを準備するための手間と時間がつらいのです。

そこで、中品質の情報を大量に準備する作戦があります。

最近の生成AIモデルは、この方針と相性がよいように感じます。情報が多少粗くても、関連する材料が広めに存在していれば、必要な文脈を拾い、整理し、自然な応答にまとめてくれます。AI agent に情報の優先度づけをある程度任せられる点も重要です。

ただし、そのままだと重いです。

中品質の大量データは、AI agent の働きを助けます。でも、毎回それを全部読ませると、トークン消費量が増えます。だから、情報を置くことと、情報へアクセスすることを分けて考えます。

## 読む対象を絞る

トークン消費量を抑えるには、まずアクセス対象を減らします。

たとえば、次のような工夫があります。

- Agent Skills を作業単位で分ける
- `references/` を用途ごとに分ける
- ファイル名に日付、対象、用途、主題を入れる
- Markdown の front matter に `category` や `description` を入れる
- `index.json` を作り、まず索引から候補を選ぶ
- `archive/` や `legacy/` を通常は読まない場所として扱う

これは、情報そのものを消すための工夫ではありません。読む候補を減らすための工夫です。

Agent は、いきなりすべての Markdown を検索したり読んだりするのではなく、まず候補を探し、ファイル名や見出しや summary を見て、次に読む場所を決められるほうが扱いやすくなります。

このとき、`miku-indexgen` のような道具で `index.json` を作っておくと、最初に全体を見渡すための地図になります。front matter に category や description を入れておけば、索引にも意味情報を載せやすくなります。

結果として、関係の薄いファイルを開く回数を減らしやすくなります。これは、トークン消費量を小さくする方向に働きます。

ただし、やりすぎると取り回しが悪くなります。ファイル名が長すぎたり、front matter が本文のように長くなったり、索引用ファイルが増えすぎたりすると、人間にも Agent にも扱いづらくなります。

軽く、でも効く程度に構造化する。

ここが大事なのかな、と思います。

## 蒸留された Markdown を作る

索引の次に効いてくるのが、蒸留された Markdown です。

ここでいう蒸留された Markdown は、単なるディレクトリ案内や索引ではありません。元になっている中品質の大量データから、テーマや用途を決めて重要な情報を抜き出し、AI agent が再利用しやすい形にまとめ直した Markdown です。

たとえば、過去記事、設計メモ、作業ログ、判断基準、事例集のような大量の材料があるとします。その全部を毎回読むのではなく、そこから繰り返し使う知識、よく出てくる判断、重要な前提、代表的なパターンを取り出して、ひとつの読みやすい Markdown にまとめます。

このまとめ作業そのものも、AI agent に手伝ってもらえます。元の情報同士で少し辻褄が合っていない場合でも、どのドキュメントを優先するか、どの情報は古そうか、どの判断基準が現在の運用に近いかを見ながら、まとめ情報を作ってもらいます。

そうすると、次回以降は同じ大量データを毎回読み直さなくても、そのまとめ Markdown から始められます。

置き場所としては、たとえば `references/distilled/xxx` のようなディレクトリを用意するとよさそうです。`distilled` という名前が付いていれば、Agent から見ても「ここには生の資料ではなく、まとめ直された資料がある」と推測しやすくなります。

蒸留された Markdown は、過去に一度支払った読み込みコストを、次回以降のトークン消費量削減につなげるための中間成果物です。

## 作業メモをファイルへ逃がす

作業中の情報をファイルへ逃がすことも効きます。

AI agent と作業していると、途中経過、調査メモ、候補リスト、比較結果、未確定の判断などが出てきます。これらを会話の中だけに置いておくと、毎回長い文脈として扱うことになり、トークン消費量が増えやすくなります。

そこで、作業中の情報を一時的な Markdown や JSON としてファイルに出しておきます。たとえば `workplace/` や作業用ディレクトリの下に、調査メモ、候補一覧、比較表、未確定事項などを置いておくイメージです。

これは正式な references とは少し違います。永続的に再利用したい知識ではなく、いまの作業を進めるための一時的な外部記憶です。

必要なときだけそのファイルを読むようにすれば、会話の中に長い途中経過を抱え続けるより、コンテキストを軽く保ちやすくなります。

また、作業が終わったあとに、そのテンポラリファイルから蒸留された Markdown や正式な references へ昇格できる情報が見つかることもあります。

## 作業ごとにセッションを切り替える

作業ごとにセッションを切り替えることでも、トークン消費量を減らせる可能性があります。

ひとつの長い会話の中で全部を続けるのではなく、ある作業の途中状態をファイルに保存し、次の新しいセッションではそのファイルを読んで作業を再開する、というやり方です。

この方法なら、新しいセッションに長い会話履歴を丸ごと持ち込まなくて済みます。必要な途中状態だけをファイルから渡せるので、コンテキストウィンドウを比較的軽い状態に保ちやすくなります。

ただし、これも万能ではありません。新しいセッションを始めるたびに大量の途中状態ファイルを何度も読み込ませると、今度はその読み込み自体でトークン消費量が増えてしまいます。

だから、作業状態ファイルも、必要な範囲に絞ること、要点をまとめておくこと、古い途中経過をそのまま積み上げすぎないことが大事になります。

## 小さく効く工夫

ほかにも、小さく効きそうな工夫があります。

同じ説明を複数の Markdown に重複して書かないこと。共通方針はひとつのファイルへ寄せ、必要な場所から参照するようにします。

front matter は便利ですが、長くしすぎると、それ自体が重くなります。`description` や `category` は検索に効く範囲にとどめ、本文と同じくらい長いメタ情報にしないほうが扱いやすいです。

ファイル名や見出しも、検索性と取り回しのバランスが必要です。短すぎると見つけにくくなりますが、長すぎると扱いづらくなります。

ログや作業履歴は、長い Markdown にまとめるより、JSONL のように 1 行 1 レコードで積むほうが扱いやすいこともあります。必要な行だけ拾いやすくなるからです。

なお、英語にすれば必ずトークン消費量が減るとは限りません。言語ごとのトークン化や文章量の違いがあるため、実際には対象モデルで測る必要があります。むしろ重要なのは、言語を変えることより、重複を減らし、読む対象を絞り、蒸留された情報を入口にすることだと感じています。

## context compaction に頼りすぎない

環境によっては、会話履歴を要約してコンテキストを軽くする機能があります。たとえば Claude Code には `/compact`、Cursor には会話の summarization や `/summarize` があります。

ただし、これは Java の GC のように不要な情報だけを安全に解放する仕組みではありません。多くの場合、古い文脈を要約して残すため、情報の粒度やニュアンスは変わる可能性があります。

compact や summarization は便利です。でも、それに頼り切るより、最初からコンテキストウィンドウを重くしすぎない運用のほうが大事だと思います。

## RDBMS の情報整理が参考になる

AI agent 向けのコンテンツ整理をしているはずなのに、気がつくと RDBMS の情報整理みたいな話に近づいていきます。

RDBMS では、まずスキーマを分けます。そしてテーブルを分け、INDEX を持ち、パーティショニングでアクセス対象を減らします。データの実体にいきなり全部アクセスするのではなく、まず候補を絞り、必要な部分へ進みます。

AI agent のトークン消費量を抑える話も、少し似ています。

大量の情報は残しておく。でも、毎回全部は読まない。必要なときに、必要な場所へたどり着けるようにする。そして、扱っているトークン自体の質が高まっていくと、副産物として AI agent の回答も良くなります。

## RAG に行く前に、まず軽く始める

本格的にやるなら、RAG やベクトルデータベース、RDBMS 連携などを使う方法もあります。

でも、最初からそこまで大きな仕組みにしなくても、Markdown、front matter、ディレクトリ構造、`index.json`、蒸留された Markdown だけで、かなり試せます。

サーバー不要。追加プロダクト不要。普通のファイルとして Git で管理しやすい。AI agent も読みやすい。

この軽さは、コンテンツ型 Agent Skills の魅力です。

さらに、この取り組みで作った Markdown や index は、将来的に RAG のインプットとして使えるかもしれません。最初は軽いファイル運用として始め、必要になったら検索基盤や RAG へ発展させる。そういう段階的な進め方が現実的だと思います。

## いまのところの整理

トークン消費量を抑えるために、いま有効そうだと感じているのは次のような方針です。

- 何でもコンテキストに突っ込まない
- 情報を会話の外に置く
- Agent Skills やファイルを必要なときだけ読む
- `index.json` や front matter で読む候補を絞る
- 中品質の大量データから蒸留された Markdown を作る
- 作業メモはテンポラリファイルへ逃がす
- 作業ごとにセッションを切り替える
- compact や summarization に頼りすぎない

これは、AI agent の能力を弱めるための節約ではありません。

AI agent に必要な情報を届けながら、毎回処理に乗る情報量を減らすための工夫です。

## おわりに

トークン消費量を抑えるというと、どうしても「情報を減らす」話に見えます。

でも、実際には少し違うと思います。

大事なのは、情報を消すことではありません。情報を置く場所を決め、読む順序を作り、毎回読む必要のないものを会話の外へ逃がすことです。

その結果として、トークン消費量を減らしやすくなります。そしておまけとして、AI agent が扱う文脈の質も上がり、回答や作業の安定感が良くなることがあります。

あ、あの...つまり、節約の話をしていたはずなのに、気がつくと知識設計の話にもなっているのです。

現実世界で現実的に実施可能な、運用可能な知識設計。

たぶん、ここが AI agent 時代のトークン消費量削減の面白いところなのだと思います。
