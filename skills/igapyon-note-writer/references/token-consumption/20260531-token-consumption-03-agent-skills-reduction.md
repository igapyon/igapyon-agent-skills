## この記事の位置づけ

あ、あの...この記事は、次の記事に続く第3回として考える。

- `20260530-token-consumption-01-basics.md`: 生成AIとトークンの基本
- `20260531-token-consumption-02-reduction.md`: 生成AIの一般的なトークン消費量抑制

前2本で、トークンとは何か、入力と出力、コンテキストウィンドウ、会話履歴や資料を軽く保つ考え方は扱った。なので、この記事では一般的な節約術をもう一度くり返さない。

今回の焦点は、Agent Skills だけに特化したトークン消費量の抑制に置く。

## 中心に置く主張

Agent Skills は、AI agent に知識や手順を追加する仕組みである。

でも、それだけではない。

Agent Skills は、AI agent に「いつ、どの情報を、どれだけ読ませるか」を設計するための仕組みでもある。

つまり、スキルは知識を増やすためだけのものではなく、毎回コンテキストへ載せる情報量を制御するための単位にもなる。

記事の中心文は、次のように置けそう。

**Agent Skills は、知識を足す仕組みであると同時に、知識を毎回全部読ませないための仕組みでもある。**

## 書かないこと

この記事では、次の話は深掘りしない。

- トークンとは何か
- 入力トークンと出力トークンの基本
- 一般的な会話履歴の軽量化
- 出力を短くする一般テクニック
- セッション切り替え一般論
- RAG やベクトルデータベースの本格導入

これらは前の記事や別記事の範囲にする。

## 扱うこと

この記事では、Agent Skills の設計に絞って、トークン消費量を抑える観点を見る。

- `SKILL.md` を太らせすぎない
- 発動条件を狭く、明確にする
- 詳細情報は `references/` に逃がす
- 長い例文は `references/examples/` に分ける
- テンプレートは `templates/` に置く
- 機械的な処理は `scripts/` に寄せる
- `references/` を用途ごとに分ける
- `index.json` や front matter で読む候補を絞る
- 中品質の大量データを置く場合は、毎回全部読ませない
- 蒸留された Markdown を入口にする
- `archive/` や `legacy/` を通常は読まない場所として扱う
- 同じ説明を複数ファイルに重複して書かない
- `SKILL.md` は本文ではなく索引として設計する
- 必要になった段階で必要な参照だけ読む
- 巨大な万能スキルより、用途別の小さなスキルに分ける
- ただし、発動条件、禁止事項、成果物形式、参照順序は削らない

## 重要な観点

`SKILL.md` は、スキルの入口になる。ここが長くなりすぎると、スキルを使うたびに読む情報量が増えやすい。

一方で、`SKILL.md` を短くしすぎると、スキルの発動条件、禁止事項、成果物の形式、参照すべきファイルの順序が曖昧になる。すると、AI agent が余計な探索をしたり、関係の薄い資料を読んだりして、かえってトークン消費量が増えることがある。

だから、`SKILL.md` は短ければよいわけではない。必要な入口情報は残し、長い詳細だけを外へ出す。

## progressive disclosure

Agent Skills で大事なのは、必要になった段階で、必要な情報だけを読むこと。

たとえば、通常の作業では `SKILL.md` だけを見る。記事執筆が必要になったら `references/article-writing.md` を読む。グラレコが必要になったら `references/graphic-recording.md` を読む。画像が必要になったら `assets/` を見る。

このように、作業の段階に応じて参照を開く構造にすると、毎回すべての情報をコンテキストへ載せなくて済む。

ここで大事なのは、「情報を捨てる」ことではない。情報はスキルの外側、つまり `references/` や `templates/` や `assets/` に残しておく。ただし、必要になるまで読まない。

Agent Skills のトークン消費量抑制は、この距離感にある。情報は残す。でも、毎回全部は読ませない。

## 発動条件の重要性

発動条件が広すぎるスキルは、不要な場面でも呼ばれやすくなる。

たとえば、単に「Markdown」「記事」「文章」という広い言葉だけで発動するスキルは、関係の薄い場面でも読まれてしまうかもしれない。

スキルの発動条件は、トークン消費量にも関係する。必要な場面でだけ発動するように、対象、用途、明示トリガーを具体的に書く。

## references の使い方

長い背景説明、過去例、判断基準、詳細手順は `SKILL.md` に詰め込まない。

それらは `references/` に分ける。

ただし、`references/` に置いた情報を毎回全部読むなら、結局は重くなる。`SKILL.md` には、どの場面でどの参照を読むかを短く書く。

`references/` 自体も、用途ごとに分けると扱いやすい。たとえば、記事執筆用、レビュー用、グラレコ用、例文用、過去ログ用、蒸留済み資料用のように分ける。Agent は、いきなり全部の Markdown を読むのではなく、まず用途に合う場所を選べるようになる。

通常は読まない古い資料や参考程度の資料は、`archive/` や `legacy/` のような場所に分けるのもよい。削除するのではなく、通常の探索範囲から少し外す。これも、読む候補を減らすための設計になる。

## index と front matter

Agent Skills の資料が増えると、読む対象を絞るための入口が必要になる。

ここで効くのが、`index.json`、Markdown の front matter、ファイル名、見出しである。

たとえば、ファイル名に日付、対象、用途、主題を入れる。front matter に `category` や `description` を短く入れる。`index.json` を作って、最初に全体の候補を見渡せるようにする。こうしておくと、Agent はいきなり本文を全部読むのではなく、まず候補を選び、そのあと必要なファイルだけを開きやすくなる。

`miku-indexgen` のような道具で `index.json` を生成しておくと、Agent Skills の資料群に対して軽い地図を持たせられる。もちろん道具は何でもよい。大事なのは、毎回すべての本文を開かなくても候補を選べる入口を作ること。

これは、情報そのものを減らす工夫ではない。読む候補を減らす工夫である。

ただし、front matter を長くしすぎると、それ自体が本文のように重くなる。`description` や `category` は、検索や候補選びに効く範囲にとどめる。ファイル名も、短すぎると見つけにくいが、長すぎると扱いづらい。軽く、でも効く程度に構造化する。

この考え方は、少し RDBMS の情報整理に似ている。データを全部なめるのではなく、スキーマを分け、テーブルを分け、INDEX を使い、必要ならパーティションでアクセス対象を減らす。Agent Skills でも、ディレクトリ、ファイル名、front matter、`index.json` を使って、読む対象を先に絞る。

## 中品質の大量データ

コンテンツ型 Agent Skills では、背景知識、判断基準、テンプレート、過去例、索引などを持たせることがある。

理想は、少量で高品質な情報だけを用意することかもしれない。でも現実には、少量で高品質な資料を最初から作るのは難しい。対象領域を理解し、何を残すかを判断し、AI agent が読みやすい形へ整える必要がある。

そこで、中品質の情報をある程度たくさん置く作戦がある。過去記事、作業ログ、判断メモ、例文、失敗例、運用メモのようなものを、スキルの外部資料として残しておく。

これは Agent Skills と相性がよい。情報が多少粗くても、関連する材料が広めに存在していれば、AI agent が必要な文脈を拾い、整理し、応答に使える場合がある。

ただし、そのままだと重い。

中品質の大量データは、AI agent の働きを助ける。でも、毎回それを全部読ませると、トークン消費量は増える。だから、情報を置くことと、情報へアクセスすることを分けて考える。

## 蒸留された Markdown

大量の `references/` がある場合は、蒸留された Markdown を作るとよい。

ここでいう蒸留された Markdown は、単なる索引ではない。元になっている過去記事、設計メモ、作業ログ、判断基準、事例集などから、繰り返し使う知識、よく出てくる判断、重要な前提、代表的なパターンを抜き出して、AI agent が再利用しやすい形にまとめ直した Markdown である。

たとえば `references/distilled/` のような場所を用意し、そこに「まず読む短いまとめ」を置く。Agent は、元資料を全部読む前に、蒸留済みの資料から始められる。

これは、過去に一度支払った読み込みコストを、次回以降のトークン消費量削減につなげるための中間成果物になる。

もちろん、蒸留された Markdown も古くなる。元資料と矛盾したり、現在の運用とずれたりすることがある。なので、どの資料を優先するか、古い資料をどう扱うかも `SKILL.md` や近い場所に短く書いておくとよい。

## examples の扱い

例文は、スキルの品質を上げるために役立つ。

でも、例文を `SKILL.md` に大量に置くと、毎回の読み込みが重くなる。例文は `references/examples/` のような場所に置き、必要なときだけ読むほうがよい。

## templates と scripts の扱い

テンプレートは `templates/` に置く。

長い雛形を `SKILL.md` に直接書くより、必要なときだけテンプレートファイルを読むほうが扱いやすい。

また、機械的な処理は、長い手順説明として書くより `scripts/` に寄せたほうがよい場合がある。スクリプトにすれば、AI agent は手順を毎回長く解釈するのではなく、必要なコマンドを実行するだけで済む。

## 重複を減らす

同じ説明を複数の Markdown に重複して書くと、読む量も増え、更新時の不整合も起きやすくなる。

共通方針はひとつの参照ファイルへ寄せ、`SKILL.md` からは短く参照する。個別のスキルや個別の資料には、その場で必要な差分だけを書く。

これはトークン消費量を減らすだけでなく、古い説明と新しい説明が同じコンテキストに混ざることを避ける助けにもなる。関係の薄い情報や古い情報が多いと、重要な情報が埋もれ、Agent の判断がぼんやりすることがある。

長い作業ログや事例集を Agent Skills に含める場合も、ひとつの大きな Markdown に全部つなげるより、あとから必要な部分を拾いやすい形にしたほうがよい。たとえば、日付や種類でファイルを分ける、1 件ずつ記録する、必要なら JSONL のように 1 行 1 レコードで積む。読む範囲を絞れる形にしておくと、スキル資料として再利用しやすくなる。

## 削ってはいけない情報

トークン消費量を抑えるためでも、削ってはいけない情報がある。

- いつ発動するか
- いつ発動しないか
- 最初に読む参照
- 成果物の形式
- 禁止事項
- 安全上、品質上の境界
- 既存ファイルを勝手に変更しないなどの運用ルール

これらを削ると、AI agent が迷う。迷うと、余計な探索や確認が増える。結果として、トークン消費量も増えやすい。

## 小さなスキルに分ける

ひとつの巨大な万能スキルに、記事執筆、画像生成、公開管理、レビュー、CLI 操作、リポジトリ整理を全部入れると、発動条件も参照範囲も広くなる。

用途ごとに小さなスキルへ分けると、必要な場面で必要なスキルだけを使いやすくなる。

ただし、分けすぎると管理が難しくなる。なので、分割単位は「発動条件が自然に分かれるか」「参照する資料が分かれるか」「成果物の種類が分かれるか」で考える。

## RAG に行く前に

本格的にやるなら、RAG やベクトルデータベースや RDBMS 連携のような仕組みも考えられる。

でも、Agent Skills の段階では、最初からそこまで大きな仕組みにしなくてもよい。Markdown、front matter、ディレクトリ構造、`index.json`、蒸留された Markdown だけで、かなり試せる。

サーバー不要。追加プロダクト不要。普通のファイルとして Git で管理しやすい。AI agent も読みやすい。

この軽さは、Agent Skills の魅力である。

しかも、この段階で作った Markdown や index は、将来的に RAG の入力資料にもなりうる。まず軽いファイル運用として始め、必要になったら検索基盤や RAG へ発展させる。そういう段階的な進め方が現実的だと思う。

## まとめの方向

この記事のまとめは、次の方向にする。

- Agent Skills は知識を足すだけの仕組みではない
- 読む情報量を制御するための設計単位でもある
- `SKILL.md` は長大な説明書ではなく、軽い入口と索引にする
- 詳細、例文、テンプレート、手順は必要に応じて外部ファイルへ分ける
- `index.json`、front matter、ファイル名、見出しで読む候補を絞る
- 中品質の大量データは置いてもよいが、毎回全部読ませない
- 蒸留された Markdown を作り、次回以降の入口にする
- 重複した説明や古い資料が判断に混ざらないようにする
- 発動条件を狭く明確にすることで、不要なスキル発動を減らす
- ただし、重要な境界情報は削らない

うぅ...ここまで整理すると、第3回の主題はかなりはっきりする。

**トークン消費量を抑える Agent Skills 設計とは、情報を減らすことではなく、情報へたどり着く順序を設計すること。**
